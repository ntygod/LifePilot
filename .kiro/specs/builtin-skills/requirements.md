## Introduction

本模块实现 LifePilot 技能系统的核心框架和内置技能插件（Phase 3，模块 9）。

技能系统是 LifePilot Agent 能力扩展的基础设施。一个 Skill 不是简单的工具别名，而是一个完整的 Agent 能力单元（Agent Capability Unit），封装了专业人格、工具权限、执行策略、记忆访问权限和独立预算。当 Skill 被激活时，它创建一个独立的 SubAgent 实例，在隔离的上下文中执行任务。

本 spec 的范围包括：
1. Skill 框架核心（数据模型、注册中心、SubAgent 工厂、工具桥接）
2. 三个内置 Skill（TodoSkill、ScheduleSkill、HabitSkill）
3. 内置 Skill 的 SQLite 持久化层（待办、日程、习惯的 CRUD）
4. 声明式记忆访问控制

本 spec 不包括：YAML 热加载、Skill 自生成/自扩展、SkillGapDetector、SkillGenerator、SandboxValidator（这些属于 Skill 系统 spec，模块 10）。

## Glossary

- **Skill_Definition**: 技能定义 record，描述一个 Agent 能力单元的完整蓝图，包含 ID、名称、描述、版本、来源、System Prompt、工具白名单、执行策略、记忆访问策略、预算约束和元数据
- **Skill_Source**: 技能来源 sealed interface，穷举三种来源类型：BUILTIN（Java 原生）、USER_DEFINED（YAML 声明式）、AUTO_GENERATED（Agent 自生成）
- **Skill_Registry**: 技能注册中心，使用 ConcurrentHashMap 管理所有 Skill 的注册、发现、搜索和生命周期
- **SubAgent_Factory**: SubAgent 工厂，从 Skill_Definition 创建运行时 SubAgent 实例，负责上下文隔离、预算分配、工具过滤和深度限制
- **Skill_To_Tool_Bridge**: 技能工具桥接服务，将已注册的 Skill 包装为 ToolContract 注册到 DynamicToolRegistry，实现 Sub-Agent-as-Tools 范式
- **Memory_Access_Policy**: 声明式记忆访问策略，定义 Skill 可读写的记忆层和实体类型，遵循默认全部拒绝原则
- **Memory_Access_Enforcer**: 记忆访问强制执行器，在运行时拦截未授权的记忆访问
- **Execution_Strategy**: 执行策略 record，定义 SubAgent 的最大步骤数、超时时间、确认模式和重试策略
- **Skill_Budget**: 技能预算 record，定义独立的 Token、步骤、时间和成本预算约束
- **Builtin_Skill_Provider**: 内置技能提供者接口，每个内置 Skill 实现此接口提供 Skill_Definition
- **Builtin_Skill_Registrar**: 内置技能注册器，在应用启动完成后按 order 顺序自动注册所有内置 Skill
- **Todo_Skill**: 待办管理内置技能，支持创建、查询、更新、删除待办事项，按优先级和截止日期排序
- **Schedule_Skill**: 日程管理内置技能，支持创建、查询、修改日程，包含冲突检测
- **Habit_Skill**: 习惯养成内置技能，支持创建习惯、打卡记录、连续天数统计和完成率分析
- **Skill_Search_Index**: 技能语义搜索索引，基于 Embedding 向量的语义匹配
- **Skill_Registry_Event**: 技能注册中心事件 sealed interface，包含 SkillRegistered、SkillUnregistered、SkillUpdated 三种事件
- **Skill_Lifecycle_Manager**: 技能生命周期管理器，协调发现、选择、激活、执行和停用五个阶段
- **Skill_Metrics_Tracker**: 技能激活指标追踪器，记录每个 Skill 的使用频率、成功率和平均耗时

## Requirements

### Requirement 1: Skill 数据模型定义

**User Story:** As a 开发者, I want 一套完整的 Skill 数据模型, so that 所有 Skill（无论来源）都能用统一的结构描述其能力蓝图

#### Acceptance Criteria

1. THE Skill_Definition SHALL 使用 Java record 实现，包含以下字段：id（唯一标识）、name（显示名称）、description（能力描述）、version（语义化版本号）、source（来源类型）、systemPrompt（专业人格）、allowedTools（工具白名单列表）、execution（执行策略）、memoryAccess（记忆访问策略）、budget（预算约束）、metadata（元数据）、preferredProviderId（LLM 偏好，可选）
2. THE Skill_Definition SHALL 在紧凑构造器中对 allowedTools 执行 List.copyOf() 防御性拷贝，确保不可变性
3. THE Skill_Definition SHALL 在紧凑构造器中校验 id、name、systemPrompt 不为空或空白，校验失败时抛出 IllegalArgumentException
4. THE Skill_Definition SHALL 提供 toDiscoverySummary() 方法，返回仅包含 id 和 description 的摘要字符串，用于渐进式发现的 Discovery 阶段
5. THE Skill_Source SHALL 使用 sealed interface 实现，permits Builtin、UserDefined、AutoGenerated 三个 record 子类型
6. THE Skill_Source SHALL 提供 priority() 默认方法，返回来源优先级数值：Builtin 为 3、UserDefined 为 2、AutoGenerated 为 1
7. THE Execution_Strategy SHALL 使用 record 实现，包含 maxSteps（1-50）、timeoutSeconds（1-600）、requireConfirmation、retryPolicy、confirmationMode 字段，并在紧凑构造器中校验值范围
8. THE Skill_Budget SHALL 使用 record 实现，包含 maxTokens、maxSteps、timeoutSeconds、maxCostCents 字段，并提供 DEFAULT（8000/10/120/50）、LIGHTWEIGHT（2000/5/30/10）、HEAVYWEIGHT（20000/20/300/200）三个预定义常量
9. THE Skill_Budget SHALL 提供 toAgentBudget() 方法，将 Skill 预算转换为 Agent 引擎的 Budget 对象

### Requirement 2: 声明式记忆访问控制

**User Story:** As a 开发者, I want 声明式的记忆访问策略, so that 每个 Skill 只能访问其声明的记忆层和实体类型，保护用户隐私

#### Acceptance Criteria

1. THE Memory_Access_Policy SHALL 使用 record 实现，包含 read（MemoryReadPermission 列表）和 write（MemoryWritePermission 列表）字段，并在紧凑构造器中执行 List.copyOf() 防御性拷贝
2. THE Memory_Access_Policy SHALL 提供 none() 静态工厂方法，返回无任何记忆访问权限的策略实例
3. THE Memory_Access_Policy SHALL 提供 canRead(layer, entityType) 方法，判断是否可以读取指定记忆层的指定实体类型，支持通配符 "*" 表示所有类型
4. THE Memory_Access_Policy SHALL 提供 canWrite(layer, entityType) 方法，判断是否可以写入指定记忆层的指定实体类型
5. WHEN SubAgent 尝试读取未声明的记忆层或实体类型时, THE Memory_Access_Enforcer SHALL 抛出 MemoryAccessViolationException 并记录 WARN 级别日志
6. WHEN SubAgent 尝试写入未声明的记忆层或实体类型时, THE Memory_Access_Enforcer SHALL 抛出 MemoryAccessViolationException 并记录 WARN 级别日志
7. WHEN 写权限的 requireApproval 为 true 时, THE Memory_Access_Enforcer SHALL 返回 true 表示需要用户确认
8. THE Memory_Access_Enforcer SHALL 支持时间范围约束检查，当查询时间点超出 MemoryReadPermission 声明的 timeRange 时抛出 MemoryAccessViolationException

### Requirement 3: Skill 注册中心

**User Story:** As a 开发者, I want 一个线程安全的 Skill 注册中心, so that 所有 Skill 可以被统一管理、发现和搜索

#### Acceptance Criteria

1. THE Skill_Registry SHALL 使用 ConcurrentHashMap 存储 Skill_Definition，支持运行时并发注册和注销
2. WHEN 注册新 Skill 时, THE Skill_Registry SHALL 先通过 SkillDefinitionValidator 校验 Skill_Definition 的合法性，校验失败时记录 WARN 日志并拒绝注册
3. WHEN 尝试覆盖已注册的 BUILTIN 来源 Skill 时, THE Skill_Registry SHALL 拒绝覆盖并记录 WARN 日志
4. WHEN 注册、注销或更新 Skill 时, THE Skill_Registry SHALL 通过 Spring ApplicationEventPublisher 发布对应的 Skill_Registry_Event（SkillRegistered、SkillUnregistered、SkillUpdated）
5. THE Skill_Registry SHALL 提供 find(skillId) 方法，返回 Optional<Skill_Definition>
6. THE Skill_Registry SHALL 提供 search(query) 方法，通过 Skill_Search_Index 进行语义搜索，返回按相似度降序排列的 Skill 列表
7. THE Skill_Registry SHALL 提供 listSummaries() 方法，返回所有 Skill 的 Discovery 摘要列表，每个摘要仅包含 id 和 description
8. THE Skill_Registry SHALL 提供 unregisterBySource(sourceType) 方法，按来源类型批量注销 Skill
9. THE Skill_Registry_Event SHALL 使用 sealed interface 实现，permits SkillRegistered、SkillUnregistered、SkillUpdated 三个 record 子类型

### Requirement 4: Skill 定义校验

**User Story:** As a 开发者, I want Skill 定义在注册前经过严格校验, so that 不合法的 Skill 定义不会进入注册中心

#### Acceptance Criteria

1. THE SkillDefinitionValidator SHALL 校验 Skill ID 格式为小写字母、数字和连字符组成，长度 1-64 字符
2. THE SkillDefinitionValidator SHALL 校验 Skill 名称长度不超过 128 字符
3. THE SkillDefinitionValidator SHALL 校验 System Prompt 长度不超过 10000 字符
4. THE SkillDefinitionValidator SHALL 校验工具列表不为空，且每个工具 ID 在已注册工具集合中存在
5. WHEN 校验 AUTO_GENERATED 来源的 Skill 时, THE SkillDefinitionValidator SHALL 额外检查 Token 预算不超过 10000、步骤数不超过 15、超时时间不超过 180 秒
6. THE SkillDefinitionValidator SHALL 返回 ValidationResult record，包含 valid 布尔值和 errors 错误信息列表

### Requirement 5: SubAgent 工厂

**User Story:** As a 开发者, I want 从 Skill 定义创建隔离的 SubAgent 实例, so that Skill 激活后在独立的上下文中执行，不影响主 Agent

#### Acceptance Criteria

1. WHEN 激活 Skill 时, THE SubAgent_Factory SHALL 从 Skill_Registry 查找 Skill_Definition，找不到时抛出 SkillActivationException
2. WHEN 当前激活深度达到 MAX_ACTIVATION_DEPTH（值为 2）时, THE SubAgent_Factory SHALL 抛出 SkillActivationException，阻止无限递归
3. WHEN 激活 Skill 时, THE SubAgent_Factory SHALL 根据 Skill_Definition 的 allowedTools 白名单过滤 DynamicToolRegistry 中的工具列表，SubAgent 只能看到声明的工具子集
4. WHEN 激活 Skill 时, THE SubAgent_Factory SHALL 从 Skill_Definition 的 budget 创建独立的 Budget 实例，SubAgent 预算耗尽不影响主 Agent
5. WHEN 激活 Skill 时, THE SubAgent_Factory SHALL 创建隔离的 AgentState，包含独立的 traceId（格式为 parentTraceId/sub-skillId-randomSuffix）
6. THE SubAgent_Factory SHALL 返回 SubAgentResult record，包含 skillId、success、output、terminationReason、tokensUsed、stepsExecuted、duration 和 traceId 字段
7. IF SubAgent 执行过程中发生异常, THEN THE SubAgent_Factory SHALL 捕获异常并返回失败的 SubAgentResult，不向上传播异常

### Requirement 6: Skill 工具桥接

**User Story:** As a 开发者, I want 将 Skill 暴露为 DynamicToolRegistry 中的工具, so that 主 AgentLoop 可以像调用普通工具一样调用 Skill

#### Acceptance Criteria

1. WHEN Skill_Registry 发布 SkillRegistered 事件时, THE Skill_To_Tool_Bridge SHALL 创建 SkillToolAdapter 并注册到 DynamicToolRegistry，工具 ID 格式为 "skill.{skillId}"
2. WHEN Skill_Registry 发布 SkillUnregistered 事件时, THE Skill_To_Tool_Bridge SHALL 从 DynamicToolRegistry 注销对应的工具
3. WHEN Skill_Registry 发布 SkillUpdated 事件时, THE Skill_To_Tool_Bridge SHALL 先注销旧工具再注册新工具
4. THE SkillToolAdapter SHALL 实现 ToolContract 接口，将 Skill 的 description 作为工具描述，将 Skill 的执行策略映射为 ToolBudget
5. WHEN AgentLoop 调用 SkillToolAdapter 的 execute 方法时, THE SkillToolAdapter SHALL 通过 SubAgent_Factory 激活对应的 Skill 并返回 SubAgentResult 转换后的 ToolResult

### Requirement 7: 内置 Skill 注册机制

**User Story:** As a 开发者, I want 内置 Skill 在应用启动时自动注册, so that 核心能力开箱即用

#### Acceptance Criteria

1. THE Builtin_Skill_Provider SHALL 定义为接口，包含 provide() 方法返回 Skill_Definition
2. THE @BuiltinSkill 注解 SHALL 包含 id（Skill ID）和 order（加载顺序）属性，标注在 Builtin_Skill_Provider 实现类上
3. WHEN 应用启动完成（ApplicationReadyEvent）时, THE Builtin_Skill_Registrar SHALL 收集所有 Builtin_Skill_Provider Bean，按 order 升序排列，依次调用 provide() 并注册到 Skill_Registry
4. IF 某个内置 Skill 注册失败, THEN THE Builtin_Skill_Registrar SHALL 记录 ERROR 日志并继续注册其他 Skill，不中断启动流程

### Requirement 8: 待办管理内置 Skill

**User Story:** As a 用户, I want 通过自然语言管理待办事项, so that 我可以高效地创建、查看、更新和完成待办

#### Acceptance Criteria

1. THE Todo_Skill SHALL 注册为 id="todo"、order=10 的内置 Skill，System Prompt 定义待办管理助手的专业人格
2. THE Todo_Skill SHALL 声明 allowedTools 包含待办 CRUD 工具：builtin.todo.create、builtin.todo.list、builtin.todo.update、builtin.todo.delete、builtin.todo.complete
3. THE Todo_Skill SHALL 声明 memoryAccess 可读 L2_EPISODIC 层的 TODO 和 SCHEDULE 实体（最近 30 天）、可读 L3_SEMANTIC 层的 PERSON 和 PROJECT 实体，可写 L2_EPISODIC 层的 TODO 实体
4. WHEN 创建待办时, THE Todo_Skill 的工具 SHALL 支持设置标题、描述、优先级（HIGH/MEDIUM/LOW）和截止日期
5. WHEN 查询待办列表时, THE Todo_Skill 的工具 SHALL 默认按优先级降序、截止日期升序排列
6. WHEN 更新待办状态时, THE Todo_Skill 的工具 SHALL 支持 PENDING → IN_PROGRESS → COMPLETED 的状态转换，拒绝非法状态转换
7. THE Todo_Skill 的持久化层 SHALL 使用 SQLite 存储待办数据，表结构包含 id、title、description、priority、status、due_date、tags_json、created_at、updated_at 字段
8. FOR ALL 待办 CRUD 操作, 创建后查询 SHALL 返回包含该待办的列表（round-trip 属性）

### Requirement 9: 日程管理内置 Skill

**User Story:** As a 用户, I want 通过自然语言管理日程安排, so that 我可以高效地创建日程并自动检测时间冲突

#### Acceptance Criteria

1. THE Schedule_Skill SHALL 注册为 id="schedule"、order=20 的内置 Skill，System Prompt 定义日程管理助手的专业人格
2. THE Schedule_Skill SHALL 声明 allowedTools 包含日程 CRUD 工具：builtin.schedule.create、builtin.schedule.list、builtin.schedule.update、builtin.schedule.delete、builtin.schedule.checkConflict
3. THE Schedule_Skill SHALL 声明 memoryAccess 可读 L2_EPISODIC 层的 SCHEDULE 和 TODO 实体（最近 90 天）、可读 L3_SEMANTIC 层的 PERSON 和 LOCATION 实体，可写 L2_EPISODIC 层的 SCHEDULE 实体
4. WHEN 创建日程时, THE Schedule_Skill 的工具 SHALL 支持设置标题、开始时间、结束时间、地点和备注
5. WHEN 创建或修改日程时, THE Schedule_Skill 的冲突检测工具 SHALL 检查新日程与已有日程的时间重叠，返回冲突的日程列表
6. THE Schedule_Skill 的持久化层 SHALL 使用 SQLite 存储日程数据，表结构包含 id、title、start_time、end_time、location、notes、created_at、updated_at 字段
7. WHILE 存在时间重叠的日程时, THE Schedule_Skill 的冲突检测 SHALL 返回所有与指定时间段重叠的日程记录
8. FOR ALL 日程 CRUD 操作, 创建后查询 SHALL 返回包含该日程的列表（round-trip 属性）

### Requirement 10: 习惯养成内置 Skill

**User Story:** As a 用户, I want 追踪和养成好习惯, so that 我可以记录打卡、查看连续天数和完成率统计

#### Acceptance Criteria

1. THE Habit_Skill SHALL 注册为 id="habit"、order=30 的内置 Skill，System Prompt 定义习惯养成教练的专业人格
2. THE Habit_Skill SHALL 声明 allowedTools 包含习惯管理工具：builtin.habit.create、builtin.habit.checkin、builtin.habit.list、builtin.habit.stats、builtin.habit.update
3. THE Habit_Skill SHALL 声明 memoryAccess 可读 L2_EPISODIC 层的 HABIT_LOG 和 HABIT 实体（最近 365 天）、可读 L3_SEMANTIC 层的 PERSON 和 HABIT 实体，可写 L2_EPISODIC 层的 HABIT_LOG 实体
4. WHEN 创建习惯时, THE Habit_Skill 的工具 SHALL 支持设置名称、频率（DAILY/WEEKLY）和目标打卡时间
5. WHEN 打卡时, THE Habit_Skill 的工具 SHALL 记录打卡时间并更新连续打卡天数（streak）
6. WHEN 查询习惯统计时, THE Habit_Skill 的工具 SHALL 返回连续打卡天数、本周完成率和本月完成率
7. THE Habit_Skill 的持久化层 SHALL 使用 SQLite 存储习惯数据，habits 表包含 id、name、frequency、target_time、current_streak、created_at、updated_at 字段；habit_logs 表包含 id、habit_id、checked_at、created_at 字段
8. WHEN 连续打卡后查询统计时, THE Habit_Skill 的统计工具 SHALL 返回的 streak 值等于实际连续打卡天数（streak 单调递增属性）
9. FOR ALL 习惯 CRUD 操作, 创建后查询 SHALL 返回包含该习惯的列表（round-trip 属性）

### Requirement 11: Skill 生命周期管理

**User Story:** As a 开发者, I want 管理 Skill 的完整生命周期, so that 并发激活受控、指标可追踪

#### Acceptance Criteria

1. THE Skill_Lifecycle_Manager SHALL 限制最大并发激活数为 MAX_CONCURRENT_ACTIVATIONS（值为 5），超出时返回失败的 SubAgentResult
2. WHEN Skill 激活时, THE Skill_Lifecycle_Manager SHALL 发布 SkillLifecycleEvent.Activated 事件
3. WHEN Skill 停用时, THE Skill_Lifecycle_Manager SHALL 发布 SkillLifecycleEvent.Deactivated 事件并递减活跃计数
4. THE Skill_Metrics_Tracker SHALL 记录每个 Skill 的总激活次数、成功次数、失败次数、总 Token 消耗和总执行时间
5. THE Skill_Metrics_Tracker SHALL 提供 getSuccessRate(skillId) 方法，返回 0.0-1.0 之间的成功率

### Requirement 12: SQLite 持久化与 Flyway 迁移

**User Story:** As a 开发者, I want 内置 Skill 的业务数据持久化到 SQLite, so that 待办、日程、习惯数据在重启后不丢失

#### Acceptance Criteria

1. THE Flyway 迁移脚本 SHALL 创建 todos 表，包含 id(TEXT PK)、title(TEXT NOT NULL)、description(TEXT)、priority(TEXT NOT NULL)、status(TEXT NOT NULL)、due_date(TEXT)、tags_json(TEXT)、created_at(TEXT NOT NULL)、updated_at(TEXT NOT NULL) 字段
2. THE Flyway 迁移脚本 SHALL 创建 schedules 表，包含 id(TEXT PK)、title(TEXT NOT NULL)、start_time(TEXT NOT NULL)、end_time(TEXT NOT NULL)、location(TEXT)、notes(TEXT)、created_at(TEXT NOT NULL)、updated_at(TEXT NOT NULL) 字段
3. THE Flyway 迁移脚本 SHALL 创建 habits 表，包含 id(TEXT PK)、name(TEXT NOT NULL)、frequency(TEXT NOT NULL)、target_time(TEXT)、current_streak(INTEGER NOT NULL DEFAULT 0)、created_at(TEXT NOT NULL)、updated_at(TEXT NOT NULL) 字段
4. THE Flyway 迁移脚本 SHALL 创建 habit_logs 表，包含 id(TEXT PK)、habit_id(TEXT NOT NULL REFERENCES habits(id))、checked_at(TEXT NOT NULL)、created_at(TEXT NOT NULL) 字段
5. THE Flyway 迁移脚本 SHALL 在 schedules 表的 start_time 和 end_time 列上创建索引，用于冲突检测查询优化
6. THE Flyway 迁移脚本 SHALL 在 habit_logs 表的 habit_id 和 checked_at 列上创建复合索引，用于打卡查询优化

### Requirement 13: Spring 自动配置

**User Story:** As a 开发者, I want Skill 模块通过 Spring AutoConfiguration 自动装配, so that 所有 Bean 通过 @Bean 方法注册，遵循编码规范

#### Acceptance Criteria

1. THE SkillAutoConfiguration SHALL 通过 @Bean 方法注册 Skill_Registry、SubAgent_Factory、Skill_To_Tool_Bridge、Memory_Access_Enforcer、Skill_Lifecycle_Manager、Skill_Metrics_Tracker、SkillDefinitionValidator 和 Builtin_Skill_Registrar
2. THE SkillAutoConfiguration SHALL 通过 @Bean 方法注册 TodoRepository、ScheduleRepository、HabitRepository 持久化组件
3. THE SkillAutoConfiguration SHALL 通过 @Bean 方法注册 TodoSkillProvider、ScheduleSkillProvider、HabitSkillProvider 内置 Skill 提供者
4. WHEN lifepilot.skills.enabled 配置为 false 时, THE SkillAutoConfiguration SHALL 不注册任何 Skill 相关 Bean
5. THE SkillConfigProperties SHALL 支持 lifepilot.skills.enabled（默认 true）和 lifepilot.skills.max-concurrent-activations（默认 5）配置项

### Requirement 14: Skill 语义搜索索引

**User Story:** As a 开发者, I want 通过语义搜索匹配最合适的 Skill, so that 主 Agent 可以根据用户请求自动选择正确的 Skill

#### Acceptance Criteria

1. WHEN Skill 注册到 Skill_Registry 时, THE Skill_Search_Index SHALL 为 Skill 的 name + description + tags 生成 Embedding 向量并缓存
2. WHEN Skill 从 Skill_Registry 注销时, THE Skill_Search_Index SHALL 移除对应的 Embedding 缓存
3. WHEN 执行语义搜索时, THE Skill_Search_Index SHALL 将查询文本转换为 Embedding 向量，通过余弦相似度匹配，返回相似度大于 0.5 的 Top-K 结果
4. THE Skill_Search_Index SHALL 使用 ConcurrentHashMap 缓存 Embedding 向量，支持并发读写
