# LifePilot 跨模块集成检查规范

本文档定义 Kiro 在 spec 规划和完成时必须执行的跨模块集成检查，防止接口漂移、集成遗漏和架构偏离。

---

## 1. Spec 规划阶段 — 接口假设验证

### 1.1 规则

规划新 spec 的 design 文档时，所有跨模块接口引用必须基于**实际源码**验证，不能仅依赖架构文档。

### 1.2 检查步骤

开始编写 design 文档前，对每个被引用的外部接口执行：

1. **定位实际源码**：在 `src/main/java/com/lifepilot/` 下找到被引用的类/接口文件
2. **核对方法签名**：确认方法名、参数类型、返回类型与 design 中的调用方式一致
3. **核对 record 字段**：确认 record 的字段名、类型与 design 中的使用方式一致
4. **核对 sealed interface permits**：确认 sealed interface 的 permits 列表包含 design 中假设的子类型
5. **核对 Spring Bean 注册**：确认被依赖的 Bean 在对应模块的 AutoConfiguration 中已注册

### 1.3 常见漂移场景

| 场景 | 示例 | 检查方法 |
|------|------|---------|
| 方法签名变更 | `SkillRegistry.register()` 参数从 `SkillDefinition` 变为 `SkillDefinition, SkillSource` | 读取实际源码确认 |
| record 字段新增/删除 | `SkillDefinition` 新增了 `providerId` 字段 | 读取实际 record 定义 |
| sealed interface 扩展 | `SkillSource` 新增了 `AutoGenerated` permit | 读取实际 sealed interface |
| 配置键变更 | `lifepilot.skill.max-steps` 改为 `lifepilot.skills.execution.max-steps` | 读取实际 Properties 类 |
| Bean 条件变更 | `@ConditionalOnProperty` 条件变更导致 Bean 未注册 | 读取实际 AutoConfiguration |

### 1.4 design 文档标注

当 design 文档引用外部模块接口时，必须标注验证来源：

```markdown
### 依赖接口验证

| 接口 | 源码位置 | 验证状态 |
|------|---------|---------|
| SkillRegistry.register() | com.lifepilot.skill.SkillRegistry | ✅ 已核对 |
| DynamicToolRegistry.register() | com.lifepilot.mcp.DynamicToolRegistry | ✅ 已核对 |
| LlmRouter.getClient() | com.lifepilot.llm.LlmRouter | ✅ 已核对 |
```

## 2. Spec 完成阶段 — 集成验证检查清单

### 2.1 每个 spec 合并到 develop 前，必须执行以下检查

#### 2.1.1 编译级集成

- [ ] `mvn compile` 全量编译通过（不仅是当前模块）
- [ ] 无编译警告涉及跨模块类型不匹配

#### 2.1.2 Spring Context 加载

- [ ] `@SpringBootTest` 集成测试能成功加载完整 ApplicationContext
- [ ] 所有 `@Autowired` 依赖注入成功，无 `NoSuchBeanDefinitionException`
- [ ] `@ConditionalOnBean` / `@ConditionalOnProperty` 条件在默认配置下满足

#### 2.1.3 跨模块接口契约

- [ ] 当前 spec 新增/修改的 public 接口，不破坏其他模块的编译
- [ ] 当前 spec 修改的 sealed interface，所有 switch 表达式仍然穷举
- [ ] 当前 spec 修改的 record 字段，所有构造调用点仍然兼容

#### 2.1.4 配置一致性

- [ ] 新增的配置键已在 `application.yml` 中声明默认值
- [ ] 配置键命名遵循 kebab-case 规范（`lifepilot.{module}.{key}`）
- [ ] 无重复或冲突的配置键

#### 2.1.5 数据库迁移

- [ ] 新增的 Flyway 迁移脚本版本号不与已有脚本冲突
- [ ] 迁移脚本在干净数据库上可成功执行
- [ ] 迁移脚本在已有数据的数据库上可成功执行（向前兼容）

### 2.2 检查执行方式

```bash
# 1. 全量编译
mvn compile -q

# 2. 全量测试（包含 Spring Context 加载测试）
mvn test

# 3. 如有数据库迁移，验证 Flyway
mvn flyway:migrate -Dflyway.url=jdbc:sqlite::memory:
```

## 3. Phase 完成阶段 — 架构对齐审计

### 3.1 触发条件

当一个 Phase 的所有模块 spec 全部完成并合并到 develop 时，执行架构对齐审计。

### 3.2 审计内容

#### 3.2.1 架构文档 vs 实际代码

对照 `docs/ARCHITECTURE.md` 和 `docs/architecture/*.md`，检查：

- [ ] 分层架构图中的模块是否都已实现
- [ ] 模块间依赖方向是否与架构图一致（上层依赖下层，不反向）
- [ ] 关键设计决策是否在代码中体现（如 StateReducer 纯函数、sealed interface 穷举等）

#### 3.2.2 接口契约完整性

- [ ] 架构文档中描述的 public API 是否都已实现
- [ ] 实际代码中新增的 public API 是否需要补充到架构文档
- [ ] 模块间通信方式是否与架构文档一致（直接调用 / Spring Event / 接口注入）

#### 3.2.3 特性文档 vs 实际功能

对照 `docs/features/*.md`，检查：

- [ ] 特性文档描述的功能是否都已实现
- [ ] 实现的功能是否与特性文档描述一致
- [ ] 如有偏差，更新特性文档或记录为后续 spec 的待办

### 3.3 偏差处理

发现架构偏差时：

1. **可接受的偏差**：实现方案优于原设计 → 更新架构文档，记录决策原因
2. **需要修正的偏差**：实现偏离了核心设计原则 → 创建 bugfix spec 修正
3. **待实现的功能**：当前 Phase 未覆盖 → 确认在后续 Phase 的模块依赖图中

## 4. 跨 Spec 接口变更协议

### 4.1 规则

当一个 spec 的实现需要修改已完成模块的 public 接口时：

1. **评估影响范围**：列出所有依赖该接口的模块
2. **向后兼容优先**：优先通过新增方法/重载实现，避免修改已有签名
3. **不可避免的破坏性变更**：
   - 在当前 spec 的 design 文档中记录变更原因
   - 同时修复所有受影响的调用点
   - 确保全量编译和测试通过

### 4.2 记录格式

在 design 文档中记录跨模块变更：

```markdown
### 跨模块接口变更

| 变更接口 | 所属模块 | 变更内容 | 影响模块 | 兼容性 |
|---------|---------|---------|---------|--------|
| SkillSource | skill | 新增 AutoGenerated permit | agent, builtin-skills | 向后兼容（新增） |
| SkillRegistry.register() | skill | 参数新增 SkillSource | builtin-skills | 需同步修改调用点 |
```

## 5. 集成测试要求

### 5.1 跨模块集成测试

每个 spec 至少包含一个跨模块集成测试，验证：

- 当前模块与直接依赖模块的协作正确性
- Spring Bean 注入链完整
- 端到端数据流通畅

### 5.2 集成测试命名

```java
// 跨模块集成测试类命名：{模块A}_{模块B}_集成测试
class SkillSystem_ToolRegistry_集成测试 {
    @Test
    void yamlSkill加载后_工具注册到DynamicToolRegistry() { ... }
}
```

### 5.3 回归测试

合并到 develop 前，运行完整测试套件（`mvn test`），确保：

- 所有已有测试仍然通过
- 无新增的编译警告
- Spring Context 加载测试通过
