# 项目（Project）— 领域级任务容器设计

## 0. 一句话说明

本次引入"**项目**"概念——用户显式创建的领域级容器，承载一次长线领域任务所需的对话、文档、知识库、定时任务、后台进程和记忆；同时把 `datastore` 从用户叙事层彻底移除（改为 LLM 内部实现），让知微的产品形态更贴近"我有几件正在做的事"的心智。

## 1. 背景与动机

### 1.1 现状的三个问题

1. **datastore 概念二义**：既是 LLM 的持久化能力，又作为用户资产被显式暴露（"资料仓库"主菜单入口）。造成"显式创建 + 隐式创建"两套入口并存，用户不理解它是什么、和自己有什么关系。
2. **隐性资源不可见**：定时任务、后台进程、生成的文档、知识库之间缺少"领域归属"。用户"给我写毕业论文"沉淀下的几十个文档和任务和平时的日常对话混在一起，找不到、管不到。
3. **LLM 领域语义不清晰**：当前没有"任务上下文边界"的显式信号，LLM 无法基于"我现在在帮你做 X"来做判断。长线任务做着做着就散了。

### 1.2 目标

- **让领域任务的资产有归属**：一件事情做下来的所有产物（对话/文档/数据/任务）可集中查看管理
- **让 LLM 的上下文有边界**：领域内聊领域的事，不被其他主题串扰
- **让 datastore 从用户叙事层消失**：能力保留给 LLM，但用户不再面对"集合""字段"这类抽象概念
- **不改变主入口范式**：对话仍然是主入口，项目是对话的组织维度，不是新的操作范式

### 1.3 不做的事（明确边界）

- **不让微微主动提议建项目**：纯用户主动。建项目是用户的决定，不是系统的判断。
- **不做项目模板/场景快捷**（投资/作业/写作…）：v1 不做，留给后续按用量反馈决定
- **不做对话跨项目迁移**：对话在哪个项目里建，就永远属于哪个。要换地方重开。
- **不做项目归档/只读模式**：v1 只有"删除"一种终态

## 2. 核心决策（锁死的设计基石）

这些在多轮 brainstorming 中已对齐：

| # | 决策 | 备注 |
|---|---|---|
| D1 | **命名叫"项目"**（Project），不叫"工作区" | 工作区在代码里已被 L1 working memory 占用；项目更贴用户心智 |
| D2 | **主账户 UI 上隐藏**，用"所有对话"承载未归属于任何项目的对话 | 对标 Qwen 侧栏设计 |
| D3 | **对话是主入口**，项目不改变交互范式 | 项目详情页核心仍是"输入框 + 对话列表" |
| D4 | **单向记忆隔离**：出不可、入可 | 详见第 4 节 |
| D5 | **datastore 在用户侧彻底移除**，LLM 工具集下线，后端代码保留（不删） | 详见第 5 节 |
| D6 | **不做主动提议、不做对话迁移、不做归档** | v1 scope 克制 |

### 3.4 主账户对应的 UI

**主账户无独立视图**——它就是"所有对话"分组，以及从各个全局管理页（如果保留的话）看到的未归属资源。

未归属于任何项目的对话/文档/定时任务/后台进程/知识库都隐式属于主账户。用户看不到"主账户"这个词，只看到"所有对话"。

**主账户知识库**：用户在"所有对话"场景下上传的文档（现有行为），以及 LLM 为主账户对话生成的文档，都会落到一个概念上的"主账户知识库"（实现上可能是 `project_id IS NULL` 的 `knowledge_bases` 行，或一个固定的默认知识库行）。第 6.2 节的数据模型按 `project_id IS NULL` 方案落地。

## 4. 隔离语义（精确表）

### 4.1 开关设计

项目创建时选择"记忆"模式，二选一：

- **不隔离**：项目聊天与主账户记忆双向读写（合流到主账户记忆池）
- **隔离**（默认）：项目聊天可读主账户记忆作为背景，但产出不写回主账户

### 4.2 记忆四层的分层处理

知微的记忆系统分 L1-L4 四层。隔离开关**并非**对所有层一视同仁——某些类型必须永远跨项目共享，否则用户体验会崩溃（例如每个项目都要重调"称我老板"）。

| 记忆类型 | 受开关控制？ | 说明 |
|---|---|---|
| **L1 Working**（短期工作记忆） | 不涉及 | 天然 session 内 |
| **L2 Episodic**（对话情节） | ✅ 受开关控制 | 对话落在哪里，情节就落在哪里 |
| **L3 Semantic：领域事实**（论文主题、项目设定） | ✅ 受开关控制 | 领域专属，不该串扰 |
| **L3 Semantic：用户偏好**（称呼、风格、人设调教） | ❌ 永远跨 | 每个项目都要重调 = 灾难 |
| **L4 Procedural**（做事方法、流程模板） | ❌ 永远跨 | 微微学到的工作方式是账户级的 |

### 4.3 资源流通规则（完整版）

假设账户里有：主账户、项目 A（不隔离）、项目 B（隔离）、项目 C（隔离）

**可流通型资源**（记忆 / 知识库 / 对话历史 — 存在"谁写入、谁能读"的流通问题）：

| 资源类型 | 主账户写入 → 谁能读 | 项目 A（不隔离）写入 → 谁能读 | 项目 B（隔离）写入 → 谁能读 |
|---|---|---|---|
| L2 情节记忆 | 主 + A（合流）+ B + C（只读继承） | 主 + A + B + C（A 写入等同主写入） | 仅 B |
| L3 领域事实 | 同上 | 同上 | 仅 B |
| L3 用户偏好 | 全局共享（不分项目） | 全局共享 | 全局共享 |
| L4 程序记忆 | 全局共享 | 全局共享 | 全局共享 |
| 知识库文档 | 主 + A + B + C（隔离项目只读继承） | 主 + A + B + C（合流） | 仅 B |
| 对话历史（搜索索引） | 主 + A + B + C（隔离项目只读继承） | 主 + A + B + C（合流） | 仅 B |

**归属型资源**（文档产出 / 定时任务 / 后台进程 — 有明确归属对象，不做跨项目流通）：

| 资源类型 | 归属规则 |
|---|---|
| 项目产出的文档 | 归属创建它的对话所在的项目；其他项目 UI 上不可见 |
| 定时任务 | 归属创建它的对话所在的项目；其他项目 UI 上不可见 |
| 后台进程 | 归属创建它的对话所在的项目；其他项目 UI 上不可见 |

**关键不变量**：
1. **隔离项目的产出永远不会出现在主账户或其他项目的读取视野**
2. **隔离项目能读到主账户的 L2/L3 领域记忆 + 知识库**（单向继承）
3. **不隔离项目 = 把项目当作主账户的一个分类视图**，记忆和知识库都与主账户合流
4. **L3 用户偏好 + L4 程序记忆不受任何项目开关影响，永远全局**

### 4.4 对话历史搜索规则

基于 4.3 的"可流通"语义推出：

- 在**主账户**搜索：返回主账户 + 所有不隔离项目的对话（后者已合流到主账户）
- 在**不隔离项目**搜索：等同主账户搜索（合流语义）
- 在**隔离项目 B** 搜索：返回 B 自己的对话 + 主账户的对话（含已合流到主账户的不隔离项目对话）；**不会**返回其他隔离项目的对话

## 5. Datastore 处置

### 5.1 用户侧：彻底移除

- 主菜单"资料仓库"入口**下架**
- `DatastoreView.vue` / `DatastoreDetailView.vue` 从路由中移除（文件保留但不再挂载）
- 所有 LLM 响应里不再出现"我已帮你创建 collection `xxx`"之类措辞

### 5.2 LLM 工具集：下线

- 从工具注册表中**移除** datastore 相关 tools
- LLM 需要结构化数据持久化时，统一产出 xlsx 文档（走 `document.create_xlsx` 等 Phase 2+ 能力）
- xlsx 文档归属当前项目的知识库/产出目录

### 5.3 后端：代码保留，能力休眠

- `DataStoreManager` / `QueryEngine` / `AggregationEngine` / `CollectionRepository` 等**代码不删**
- 配置层关闭其 auto-wiring 或不再被 ToolRegistry 引用
- 未来如果观察到 xlsx 确实 hold 不住某些场景（极大量高频 CRUD），再决定复活

### 5.4 已有 datastore 数据的处理

知微是未上线的新项目（参见记忆 `feedback_no_compat.md`），**不做数据迁移**。开发环境里已有的 datastore 数据作为历史痕迹存在，用户不可见即可。

## 6. 后端改动范围

### 6.1 数据模型新增

新增一张 `projects` 表（名字待定，**避免用 `workspaces`**——已被 L1 占用）：

```sql
CREATE TABLE projects (
    id           TEXT PRIMARY KEY,           -- UUID
    user_id      TEXT NOT NULL,
    name         TEXT NOT NULL,
    instructions TEXT,                        -- 指示词，最大 1000 字符
    isolation    TEXT NOT NULL DEFAULT 'ISOLATED',  -- 'ISOLATED' | 'SHARED'
    created_at   TEXT NOT NULL,               -- ISO 8601
    updated_at   TEXT NOT NULL,
    UNIQUE(user_id, name)
);

CREATE INDEX idx_projects_user ON projects(user_id);
```

### 6.2 现有表加 `project_id` 字段

必须加的（核心关联）：
- `conversations`（对话归属）
- `knowledge_bases`（知识库归属）
- `documents`（文档归属，Phase 2 的表名以实际为准）
- `scheduled_tasks`（定时任务归属）
- `background_processes`（后台进程归属）

`project_id` 语义：
- `NULL` = 归属主账户
- 非 NULL = 归属具体项目

为什么不加"default_project" 行而用 NULL：避免所有老数据和主账户对话都强制关联一行假项目，减少迁移复杂度，语义也更自然（"没有项目"是一个合法状态，不是"属于默认项目"）。

### 6.3 记忆 scope 扩展

`memory/scope` 包已有 `MemorySpace` / `MemoryScope` / `MemoryReadFilter` 基础设施。扩展方式：

- `MemorySpaceType` 新增 `PROJECT` 枚举值（当前可能只有 GLOBAL / SESSION）
- 每个项目创建时对应一个 `MemorySpace` 行
- **隔离项目**：有自己独立的 MemorySpace，`MemoryReadFilter` 允许读主账户 space + 自己 space
- **不隔离项目**：共用主账户的 MemorySpace（或单独建但读写都路由到主）
- 记忆写入时 `MemoryWriteContext` 携带 `projectId`，按开关决定落哪个 space
- L3 用户偏好 / L4 程序记忆的写入路径**绕过项目 scope**，始终落全局（依赖现有的 `MemoryOriginType` 或新增一个标记）

### 6.4 关键服务新增

- `ProjectService`：CRUD + 唯一性校验 + 删除级联
- `ProjectContextResolver`：解析当前请求落在哪个项目里（URL / 对话元数据 / session state）
- **记忆检索层改造**：`MemoryReadFilter.buildForProject(projectId, isolation)` 返回正确的 space 过滤器
- **知识库检索层改造**：`SessionKnowledgeScopeResolver` 要支持项目级范围（可能已有类似能力，要对齐）
- **对话创建接口**：建对话时必须带 `project_id`（可 null）
- **定时任务/后台进程**：创建 API 加 `project_id` 参数

### 6.5 Flyway 迁移

当前最新 V14，新增：
- `V15__create_projects_table.sql`
- `V16__add_project_id_to_conversations.sql`
- `V17__add_project_id_to_knowledge_bases.sql`
- `V18__add_project_id_to_documents.sql`（如 documents 表已在 Phase 2 建立）
- `V19__add_project_id_to_scheduled_tasks.sql`
- `V20__add_project_id_to_background_processes.sql`

具体拆分顺序在实现计划里定。

9. 项目删除（级联清理关联对话、文档、任务、知识库）

### 9.2 v1 不做（延后或不做）

- 项目归档/只读
- 对话跨项目迁移
- 微微主动提议建项目
- 项目场景模板（投资/作业/写作/健康/旅行）
- 项目级分析统计
- 项目间的批量操作（跨项目搜索、跨项目合并）
- 项目成员/协作（知微是单机本地助手，不涉及）

## 10. 关键风险与对策

| 风险 | 对策 |
|---|---|
| 记忆 scope 改造波及面大，回归风险高 | 分阶段：先做"隔离项目"的写入路由，再做读取继承；每步加集成测试 |
| 开发环境已有对话/知识库数据没有 project_id | 知微是未上线新项目，无兼容负担；`project_id IS NULL` 语义为"归属主账户"，加字段时 default NULL 即可，已有数据天然变成"所有对话"的一部分 |
| datastore 下架后 LLM 可能仍尝试调用 | 工具注册表移除 + Prompt 层不再提及 + 集成测试验证 LLM 不再产生 datastore 相关动作 |
| 项目改名后 URL 路由如何稳定 | 路由用 `projectId` 而非 name；name 是显示值，可随时改 |
| 删除项目时级联清理失败（文件/知识库索引残留） | 删除流程用事务或补偿任务；失败场景有重试 + 人工介入入口 |

## 11. 与 Qwen 项目的差异对照

| 维度 | Qwen | 知微 v1 |
|---|---|---|
| 命名 | 项目 | 项目 ✓ |
| 侧栏 | 项目分组 + 所有对话分组 | 同 ✓ |
| 主视图 | 输入框 + 对话列表（清爽款） | 同 ✓ |
| 创建字段 | 名字 + 场景模板 + 记忆 + 指示词 + 文件 | 名字 + 记忆 + 指示词 + 文件（场景模板延后） |
| 记忆模式 | 默认 / 仅限项目（行为与知微一致） | 不隔离 / 隔离（文案不同但语义对齐） |
| 默认记忆模式 | "默认"（共享） | 隔离 ✓（用户主动建项目 = 想圈起来） |
| 显式归属的隐性资源 | 主要是文件/知识库 | 知识库 + 文档 + 定时任务 + 后台进程（知微覆盖范围更广） |

## 12. 验收标准（供实现计划拆解参考）

1. 用户可在侧栏建项目、重命名、删除
2. 在项目里发起的对话、上传的知识库文档、排的定时任务、启动的后台进程，均正确打上 `project_id`
3. 在隔离项目里：
   - 能检索到主账户知识库的内容（RAG）
   - 能访问主账户的 L2/L3 领域记忆（注入上下文）
   - 写入的记忆/产出**不**出现在主账户或其他项目的任何读取视野
4. 在不隔离项目里：记忆与主账户合流（双向可见）
5. 无论开关如何，L3 用户偏好（称呼 / 风格）和 L4 程序记忆跨所有项目生效
6. Datastore 主菜单入口消失，路由访问 `/datastore` 404（或跳转到首页）
7. LLM 在对话中不再尝试调用任何 datastore 工具
8. 删除项目时，关联的对话/文档/知识库/任务/进程一并清理；L3/L4 的全局记忆不受影响

## 附录 A：术语表

- **项目（Project）**：用户显式创建的领域级任务容器
- **主账户**：用户账户本身，包含未归属于任何项目的所有对话和资源；UI 上以"所有对话"分组体现，不出现"主账户"字样
- **隔离模式**：单向隔离——项目能读主账户，但产出不写回主账户
- **不隔离模式**：项目与主账户记忆双向合流
- **指示词（Instructions）**：项目级 custom instructions，注入到该项目对话的 system prompt
- **MemorySpace**：记忆系统中的 scope 容器，每个项目对应至少一个 MemorySpace
- **主账户 MemorySpace**：存放未归属项目的所有记忆；所有隔离项目都能**只读**访问它
