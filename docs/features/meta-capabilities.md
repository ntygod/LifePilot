# 元能力系统（Meta-Capabilities）

> 本文档描述 LifePilot 的自扩展基础设施 — 让系统能自我发现、自我扩展、自我解释的内置元能力。

> 状态：📋 规划中（依赖 Skill 系统、MCP 协议、多 Agent 协作、插件市场）

## 1. 概述

### 1.1 什么是元能力？

元能力不是具体的业务功能（如查天气、记待办），而是**让系统获取新能力的能力**。类比操作系统：

- 业务 Skill = 应用程序（Word、Chrome）
- 元能力 = 应用商店 + 系统设置 + 帮助中心

用户不需要手动编辑配置文件或浏览 GitHub 仓库，只需用自然语言描述需求，系统就能自动发现、安装、配置所需的扩展。

### 1.2 设计原则

- **对话驱动**：所有元操作通过自然语言触发，不需要用户了解技术细节
- **安全优先**：外部扩展必须经过验证流程，高风险操作需用户确认
- **渐进发现**：从自省（了解已有能力）→ 发现（搜索新能力）→ 安装（获取新能力）→ 配置（调整能力），逐步引导用户
- **多源聚合**：Skill 和 MCP 的发现不局限于单一来源，聚合本系统市场和业界开源生态

### 1.3 元能力全景

```
┌─────────────────────────────────────────────────────┐
│                    用户自然语言                        │
│         "我需要查汇率" / "帮我连接 GitHub"             │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌─────────────────────────────────────────────────────┐
│              Agent 意图识别 + 能力缺口检测              │
│         现有 Skill/Tool 无法满足 → 触发元能力           │
└──────────────────────┬──────────────────────────────┘
                       ▼
┌──────────┬───────────┬───────────┬──────────┬────────────┐
│ 自省能力  │ Skill 发现 │ MCP 发现  │ 基础工具  │ 引导 Agent  │
│          │  与安装    │  与配置   │          │            │
├──────────┼───────────┼───────────┼──────────┼────────────┤
│ 列出已有  │ 搜索市场   │ 搜索注册  │ 环境感知  │ 新用户引导  │
│ 能力并    │ + 开源生态 │ 中心      │ 信息获取  │ + 场景推荐  │
│ 解释用途  │ → 安装验证 │ → 配置连接│ 推理辅助  │            │
│          │           │          │ 交互控制  │            │
└──────────┴───────────┴───────────┴──────────┴────────────┘
```

## 2. 系统自省（System Introspection）

### 2.1 功能定位

系统自省是元能力的入口 — 让用户了解 LifePilot 当前能做什么。新用户的第一个问题往往是"你能做什么？"，自省能力让 Agent 能准确、完整地回答这个问题。

### 2.2 实现方式

Java 原生内置 Skill（`SystemIntrospectionSkillProvider`），与 Todo/Schedule/Habit/Memory 同级，系统启动时自动注册。

### 2.3 提供的工具

| 工具 ID | 功能 | 输入 | 输出 |
|---------|------|------|------|
| `system.list-capabilities` | 列出所有已注册的能力 | 可选过滤：类型（skill/agent/mcp/workflow/tool） | 能力清单（ID、名称、描述、来源、状态） |
| `system.explain` | 解释某个能力的详细用途 | 能力 ID | 详细说明（功能、使用场景、示例对话、依赖关系） |
| `system.status` | 系统运行状态概览 | 无 | LLM 连接状态、MCP Server 状态、已注册 Skill/Agent/Tool 数量、记忆统计 |
| `system.suggest` | 根据用户描述推荐能力 | 用户需求描述 | 匹配的已有能力列表，或建议安装的新能力 |

### 2.4 数据来源

自省工具从以下注册中心聚合信息：

- `SkillRegistry` — 所有已注册 Skill（Builtin + UserDefined + AutoGenerated）
- `AgentRegistry` — 所有已注册 Agent（Builtin + MarkdownDefined）
- `DynamicToolRegistry` — 所有已注册工具（Builtin + Skill + MCP）
- `WorkflowRegistry` — 所有已注册工作流
- `McpClient` 连接池 — 所有已配置的 MCP Server 及其连接状态

### 2.5 对话示例

```
你：你能做什么？

LifePilot：我目前有以下能力：

         📋 核心 Skill（4 个）
         • 待办管理 — 创建、查询、完成待办事项
         • 日程管理 — 安排日程、冲突检测、提醒
         • 习惯养成 — 打卡、统计、鼓励
         • 记忆管理 — 搜索、回忆、关联

         🤖 专家 Agent（3 个）
         • 生活教练 — Socratic 提问法引导反思
         • 规划师 — 目标分解和时间规划
         • 写作助手 — 长文撰写、润色、翻译

         🔌 MCP 工具（2 个 Server）
         • filesystem — 文件读写操作
         • github — GitHub 仓库管理

         💡 想要更多能力？告诉我你需要什么，我可以帮你搜索和安装。
```

```

         2. 🔍 搜索 Skill 市场 — 看看有没有 Notion 集成 Skill

## 3. Skill 发现与安装（Skill Discovery）

### 3.1 功能定位

当用户需要系统尚不具备的能力时，Skill 发现能力帮助用户从多个来源搜索、评估、安装合适的 Skill。

### 3.2 实现方式

Java 原生内置 Skill（`SkillDiscoverySkillProvider`），封装已有的 `MarketplaceService` 并扩展外部源支持。

### 3.3 数据来源分层

```
┌─────────────────────────────────────────────┐
│            Skill 发现统一接口                  │
│         SkillDiscoverySkillProvider           │
└──────────────────┬──────────────────────────┘
                   ▼
┌─────────────┬────────────────────────────────┐
│  主要来源    │  扩展来源                       │
├─────────────┼────────────────────────────────┤
│ LifePilot   │  开源 Agent Skills 生态         │
│ Marketplace │                                │
│             │  • LobeHub Skills Marketplace   │
│ • GitHub    │  • AgentSkillsHub（458+ Skills）│
│   仓库索引  │  • GitHub 搜索（agent-skills    │
│ • 已有的    │    topic）                      │
│   IndexMgr  │                                │
│   + Skill   │  格式适配层：                    │
│   Installer │  外部格式 → LifePilot Markdown  │
│             │  Frontmatter 格式               │
└─────────────┴────────────────────────────────┘
```

**主要来源 — LifePilot Marketplace**：
- 已有完整基础设施（IndexManager + SkillInstaller + SecurityAuditor）
- Skill 格式原生兼容，安装后直接可用
- 经过 SkillValidationPipeline 三重验证（格式 → 安全 → 沙箱）

**扩展来源 — 开源 Agent Skills 生态**：
- LobeHub Skills Marketplace（2900+ Skills，社区最活跃）
- AgentSkillsHub（458+ Skills，安全评级 A-F）
- GitHub 搜索（`agent-skills` / `mcp-skill` topic）
- 需要格式转换层：外部 Skill 的 Markdown 指令 + 元数据 → LifePilot Frontmatter 格式

### 3.4 格式适配

外部 Skill 的核心结构（以 Anthropic Agent Skills 标准为例）：

```
.agent/skills/{skill-name}/
├── SKILL.md          # 指令 + 元数据
├── scripts/          # 辅助脚本
└── templates/        # 模板文件
```

LifePilot 的 Skill 格式：

```
~/.lifepilot/skills/{skill-name}/
└── SKILL.md          # YAML Frontmatter + Markdown 指令体
```

适配映射：

| 外部字段 | LifePilot 字段 | 说明 |
|---------|---------------|------|
| name | id + name | 外部 name 同时映射为 ID（kebab-case）和显示名 |
| description | description | 直接映射 |
| instructions（Markdown 正文） | system-prompt（Markdown body） | 直接映射为指令体 |
| tools（如有声明） | allowed-tools | 映射为工具权限列表 |
| — | source: MARKETPLACE | 标记来源为市场安装 |
| — | version | 从外部元数据提取或默认 "1.0" |

适配层做的事情很薄：读取外部 Skill 的元数据和指令 → 生成 LifePilot Frontmatter 格式的 SKILL.md → 走正常的 SkillValidationPipeline 验证 → 安装到用户 Skill 目录。

### 3.5 提供的工具

| 工具 ID | 功能 | 输入 | 输出 |
|---------|------|------|------|
| `skill-discovery.search` | 搜索可用 Skill | 关键词、标签、来源过滤 | 匹配的 Skill 列表（名称、描述、来源、评级、下载量） |
| `skill-discovery.detail` | 查看 Skill 详情 | Skill 包 ID | 详细信息（功能说明、工具列表、安全评级、用户评价） |
| `skill-discovery.install` | 安装 Skill | Skill 包 ID、是否确认高风险 | 安装结果（成功/失败、安全报告） |
| `skill-discovery.uninstall` | 卸载 Skill | Skill 包 ID | 卸载结果 |
| `skill-discovery.check-updates` | 检查已安装 Skill 的更新 | 无 | 有更新的 Skill 列表 |

### 3.6 安全机制

- 所有外部 Skill 安装前必须经过 SkillValidationPipeline 三重验证
- 外部来源的 Skill 首次安装标记为 HIGH 风险，需用户确认
- 安装记录持久化到 `installed_skills` 表，支持回溯和卸载
- 外部 Skill 的 `scripts/` 目录内容不自动执行，仅作为参考文档导入

### 3.7 对话示例

```
你：我需要查汇率

LifePilot：🔍 正在搜索汇率相关 Skill...

         找到 2 个匹配结果：

         1. 📦 exchange-rate-query（LifePilot 市场）
            ⭐ 安全评级：A | 下载量：1,200
            功能：实时汇率查询，支持 150+ 货币对
            来源：exchangerate.host API

         2. 📦 currency-converter（LobeHub）
            ⭐ 社区评分：4.5 | 安装量：8,500
            功能：货币转换 + 历史汇率趋势
            需要格式适配

         推荐安装 #1（原生格式，验证更完整）。要安装吗？

你：安装第一个

LifePilot：🔒 安全验证中...
         ✅ 格式校验通过
         ✅ 安全检查通过（无危险操作）
         ✅ 沙箱试运行通过

         📦 exchange-rate-query 安装成功！

         💱 现在就帮你查：今日汇率 1 USD = 7.24 CNY

## 4. MCP 发现与配置（MCP Discovery）

### 4.1 功能定位

MCP 是开放标准协议，生态中已有大量现成的 Server（文件系统、GitHub、数据库、Notion 等）。MCP 发现能力让用户通过对话即可搜索、安装、配置 MCP Server，无需手动编辑 `application.yml`。

### 4.2 实现方式

Java 原生内置 Skill（`McpDiscoverySkillProvider`），通过 HTTP 客户端查询外部注册中心，操作本地 MCP 配置。

### 4.3 数据来源

MCP 没有"本系统市场"的概念，直接对接业界已有的开源注册中心：

| 来源 | 说明 | 接入方式 |
|------|------|---------|
| MCP 官方 Registry | 2025.9 上线，Anthropic/OpenAI/Google/Microsoft/AWS 共同维护 | REST API 查询 |
| Smithery Registry | 社区最活跃的 MCP Server 目录 | REST API 查询 |
| npm / PyPI | 直接按包名安装（如 `@modelcontextprotocol/server-filesystem`） | 包管理器命令 |

### 4.4 提供的工具

| 工具 ID | 功能 | 输入 | 输出 |
|---------|------|------|------|
| `mcp-discovery.search` | 搜索可用 MCP Server | 关键词或自然语言描述 | 匹配的 Server 列表（名称、描述、传输类型、安装命令） |
| `mcp-discovery.install` | 安装并配置 MCP Server | Server 名称、传输类型、参数、环境变量 | 配置写入结果 + 连接测试结果 |
| `mcp-discovery.list` | 列出已配置的 MCP Server | 无 | Server 列表（名称、状态、工具数量） |
| `mcp-discovery.remove` | 移除 MCP Server 配置 | Server 名称 | 移除结果 |
| `mcp-discovery.test` | 测试 MCP Server 连接 | Server 名称 | 连接状态、可用工具列表 |

### 4.5 安装流程

```
用户："帮我连接 GitHub"
  ↓
1. 搜索注册中心 → 找到 @modelcontextprotocol/server-github
  ↓
2. 检查前置条件 → 需要 npx、需要 GITHUB_PERSONAL_ACCESS_TOKEN
  ↓
3. 引导用户配置 → "请提供你的 GitHub Personal Access Token"
  ↓
4. 写入配置 → 更新 application.yml 的 lifepilot.mcp.servers
  ↓
5. 初始化连接 → McpClient.initialize() + listTools()
  ↓
6. 确认可用 → "GitHub MCP Server 已连接，提供 12 个工具"
```

### 4.6 安全机制

- MCP Server 安装需要用户确认（HIGH 风险操作）
- 环境变量（API Key 等）引导用户通过环境变量设置，不写入配置文件
- 安装前检查前置条件（npx / uv / Docker 是否可用）
- 连接测试失败时自动回滚配置变更

### 4.7 对话示例

```
你：我想连接 GitHub 管理我的仓库

LifePilot：🔍 正在搜索 GitHub 相关的 MCP Server...

         找到：@modelcontextprotocol/server-github
         • 官方维护，传输类型：stdio
         • 提供 12 个工具：创建 Issue、管理 PR、搜索代码等
         • 需要：npx + GitHub Personal Access Token

         要安装吗？

你：安装

LifePilot：请提供你的 GitHub Personal Access Token。
         （在 GitHub Settings → Developer settings → Personal access tokens 创建）

你：ghp_xxxxxxxxxxxx

LifePilot：🔧 配置中...
         ✅ 环境变量已设置
         ✅ MCP Server 配置已写入
         ✅ 连接测试通过（12 个工具可用）

## 5. 引导 Agent（Onboarding Guide）

### 5.1 功能定位

新用户首次使用 LifePilot 时，引导 Agent 主动介绍系统能力，根据用户的使用场景推荐合适的 Skill 组合、Agent 配置和工作流设置。

### 5.2 实现方式

Markdown 定义的预设 Agent（`onboarding-guide.md`），放置在 `src/main/resources/preset-agents/` 目录，系统启动时通过 `AgentMarkdownLoader` 自动加载注册。

### 5.3 核心能力

- 了解 LifePilot 所有功能模块，能用通俗语言解释每个模块的价值
- 调用 `system.list-capabilities` 和 `system.suggest` 工具，基于实际注册状态回答
- 根据用户描述的使用场景（学生、职场人、自由职业者等），推荐个性化的能力组合
- 引导用户完成关键配置（LLM 服务商、MCP Server、首个 Skill）
- 首次启动时自动激活，后续可通过"帮我重新设置"再次触发

### 5.4 对话示例

```
（首次启动）

LifePilot：👋 你好！我是 LifePilot，你的 AI 伙伴。

         我可以帮你管理待办、安排日程、养成习惯，还能通过扩展获得更多能力。

LifePilot：了解！推荐你这样开始：

         ✅ 已就绪：
         • 待办管理、日程管理、习惯养成（内置，直接可用）
         • 记忆系统（会记住你的偏好和习惯）

## 6. 内置工作流（Built-in Workflows）

### 6.1 每日摘要（daily-digest）

**触发方式**：Cron 触发（默认每天 08:00）或用户手动触发

**执行流程**：
1. 调用 `skill.schedule-query` 获取今日日程
2. 调用 `skill.todo-query` 获取待办进度
3. 调用 `skill.habit-query` 获取习惯打卡状态
4. 汇总为结构化摘要，通过当前活跃渠道推送给用户

**输出示例**：
```
📊 早安！今日概览（3月7日 周六）

📅 日程（2 项）
  09:00 团队周会
  14:00 客户回访

📋 待办（3 项未完成）
  🔴 提交Q1报告（明天截止）
  🟡 回复合作方案邮件
  🟢 整理会议纪要

🎯 习惯
  晨跑：待打卡（连续 15 天 🔥）
  阅读：待打卡
```

### 6.2 Skill 更新检查（skill-update-check）

**触发方式**：Cron 触发（默认每周一 10:00）

**执行流程**：
1. 调用 `skill-discovery.check-updates` 检查已安装 Skill 的更新
2. 有更新时通知用户，列出变更内容
3. 用户确认后执行升级

## 7. 与现有模块的关系

### 7.1 依赖关系

| 元能力 | 依赖模块 | 说明 |
|--------|---------|------|
| 基础工具 | DynamicToolRegistry、MemoryRetriever（可选） | 环境感知和推理辅助无外部依赖；web.search 需要搜索引擎 API Key |
| 系统自省 | SkillRegistry、AgentRegistry、DynamicToolRegistry、WorkflowRegistry | 聚合各注册中心信息 |
| Skill 发现 | MarketplaceService（模块 25）、SkillValidationPipeline（模块 10） | 封装已有市场基础设施 + 扩展外部源 |
| MCP 发现 | McpClient（模块 4）、McpConfigProperties | 操作 MCP 配置和连接 |
| 引导 Agent | AgentRegistry（模块 21）、系统自省 Skill | 依赖自省工具获取实时能力信息 |
| 内置工作流 | WorkflowEngine（模块 15）、内置 Skill | 编排已有 Skill 的工具 |

### 7.2 与 Skill 自扩展（SkillGenerator）的关系

SkillGenerator 是 Agent 运行时自动生成 Skill 的能力（已实现），Skill 发现是从外部市场搜索已有 Skill 的能力。两者互补：

- **优先级**：先搜索市场（经过验证的 Skill 更可靠）→ 市场没有再自动生成
- **触发时机**：Agent 检测到能力缺口时，先调用 `skill-discovery.search`，无结果再调用 `SkillGenerator`
- **质量差异**：市场 Skill 经过社区验证和安全审计，自生成 Skill 是即时创建的

### 7.3 实现优先级

建议按以下顺序实现（每个可作为独立 spec）：

1. **基础工具** — 最基础的 Agent 感官，零外部依赖，所有后续能力都受益
2. **系统自省** — 元能力入口，无外部依赖，立即可用
3. **Skill 发现** — 封装已有 MarketplaceService，增量开发
4. **MCP 发现** — 需要对接外部注册中心 API
5. **引导 Agent** — 依赖自省和发现能力
6. **内置工作流** — 依赖工作流引擎 + 内置 Skill

## 8. 基础工具（Built-in Tools）

### 8.1 现状分析

当前系统已有 30+ 个内置工具，但全部是**领域工具**（todo/schedule/habit/memory/sync），由各 BuiltinSkillProvider 注册。缺少的是 Agent 正常运作所需的**基础设施工具** — 不属于任何业务 Skill，而是 Agent 自身的"感官"和"手脚"。

类比人类：领域工具是"专业技能"（会计、编程），基础工具是"基本能力"（看、听、算、问）。一个没有基础工具的 Agent，就像一个不知道今天几号、无法上网查资料、遇到不确定也不会问用户的"专家"。

### 8.2 基础工具清单

基础工具按功能分为四类：**环境感知**、**信息获取**、**推理辅助**、**交互控制**。

#### 8.2.1 环境感知工具

Agent 需要感知当前环境上下文，才能做出合理决策。

| 工具 ID | 名称 | 功能 | 风险等级 | 说明 |
|---------|------|------|---------|------|
| `builtin.env.datetime` | 当前日期时间 | 返回当前日期、时间、星期、时区 | LOW | LLM 训练数据有截止日期，不知道"今天"是哪天。日程管理、截止日期判断、"明天"解析都依赖此工具 |
| `builtin.env.user-profile` | 用户画像 | 返回用户偏好设置（语言、时区、通知偏好等） | LOW | 从配置和记忆系统聚合，避免每次对话重复询问 |

#### 8.2.2 信息获取工具

Agent 需要从外部世界获取实时信息，而非仅依赖训练数据。

| 工具 ID | 名称 | 功能 | 风险等级 | 说明 |
|---------|------|------|---------|------|
| `builtin.web.search` | 网页搜索 | 通过搜索引擎 API 搜索互联网信息 | LOW | 支持 Google / Bing / DuckDuckGo（可配置），返回标题 + 摘要 + URL |
| `builtin.web.fetch` | 网页内容提取 | 获取指定 URL 的页面内容并提取正文 | LOW | 基于 Jsoup 解析 HTML，提取正文、标题、结构化数据。配合 `web.search` 使用 |
| `builtin.web.fetch` 提取的内容可选写入知识图谱（带时效标记），避免重复抓取 |

#### 8.2.3 推理辅助工具

帮助 Agent 在复杂推理过程中保持准确性。

| 工具 ID | 名称 | 功能 | 风险等级 | 说明 |
|---------|------|------|---------|------|
| `builtin.reason.think` | 思考草稿板 | Agent 将中间推理过程写入草稿板，不输出给用户 | LOW | 参考 Anthropic 的 extended thinking 模式。复杂多步推理时，Agent 先"想清楚"再回答，减少幻觉。输入为思考内容，输出为确认存储 |
| `builtin.reason.calculate` | 数学计算 | 执行精确数学运算（四则运算、百分比、日期差等） | LOW | LLM 的数学能力不可靠（尤其大数运算）。提供精确计算能力，避免"9.11 > 9.9"类错误 |

#### 8.2.4 交互控制工具

Agent 需要在适当时机与用户交互，而非自作主张。

| 工具 ID | 名称 | 功能 | 风险等级 | 说明 |
|---------|------|------|---------|------|
| `builtin.interact.confirm` | 用户确认 | 向用户展示操作摘要并请求确认（是/否） | LOW | 高风险操作前的确认机制。GuardrailEngine 判定需要确认时，Agent 调用此工具暂停执行 |
| `builtin.interact.choose` | 用户选择 | 向用户展示多个选项并请求选择 | LOW | 当 Agent 无法自行决策时（如多个匹配结果），让用户做最终选择 |
| `builtin.interact.input` | 用户输入 | 请求用户提供特定信息（如 API Key、文件路径） | LOW | MCP 配置、外部服务连接等场景需要用户提供敏感信息 |

### 8.4 实现方式

基础工具通过独立的 `InfraToolProvider`（Java 原生 `BuiltinSkillProvider`）注册，与业务 Skill 解耦：

- `InfraToolProvider` 不属于任何业务 Skill，直接注册到 `DynamicToolRegistry`
- 所有基础工具默认对所有 Agent 可用（不受 `allowedToolIds` 白名单限制）
- 基础工具的 `tags` 统一包含 `"infrastructure"` 标签，便于过滤和管理
- 风险等级全部为 LOW（只读或用户交互），不触发 GuardrailEngine 审批流程

### 8.5 与 MCP 工具的关系

部分基础工具的功能可以通过 MCP Server 实现（如 `@anthropic/web-search` MCP Server），但基础工具必须内置的原因：

- **零配置可用**：用户不需要安装任何 MCP Server 就能使用基础能力
- **无外部依赖**：不依赖 npx / uv / Docker，单 JAR 启动即可
- **性能最优**：进程内调用，无 JSON-RPC 序列化和进程间通信开销
- **离线可用**：`datetime`、`calculate`、`think`、交互工具在无网络时仍可工作

如果用户安装了功能更强的 MCP 工具（如专业搜索引擎 MCP），三层优先级机制会自动处理：MCP 工具和内置工具共存，Agent 根据场景选择最合适的。

### 8.6 不内置的工具（交给 Skill / MCP）

以下能力虽然常见，但不适合作为基础工具内置：

| 能力 | 不内置原因 | 推荐方案 |
|------|-----------|---------|
| 天气查询 | 需要 API Key，非通用基础能力 | Skill 市场安装 |
| 邮件发送 | 高风险 + 需要 SMTP 配置 | MCP Server |
| 文件系统操作 | 高风险 + 已有 MCP Server | `@modelcontextprotocol/server-filesystem` |
| 数据库查询 | 高风险 + 数据库类型多样 | MCP Server |
| 代码执行 | 已有 SandboxBooter 模块（模块 16） | 通过沙箱系统执行 |
| 翻译 | 需要 LLM 调用，LLM 本身已具备 | Agent 直接处理 |

## 9. 工具权限模型（Tool Permission Model）

### 9.1 核心概念：一切皆 Tool

在 LifePilot 中，LLM 能直接调用的只有 `DynamicToolRegistry` 中注册的 Tool。**Skill 和 Agent 本身不是 Tool，不能被 LLM 直接检索或调用**，它们通过桥接机制在运行时被转换为 Tool 注册到 Registry 中：

| 概念 | 本质 | 桥接机制 | 注册到 Registry 的 Tool ID |
|------|------|---------|--------------------------|
| Agent | 独立的 AgentLoop 执行单元 | `HandoffToolFactory.createHandoffTool()` | `handoff_to_{agentId}` |
| Skill | SubAgent 模式的能力单元 | `SkillToToolBridge.onSkillRegistered()` | `skill.{skillId}` |
| Tool | 原子操作（直接执行） | 直接注册 | 原始 ID（如 `builtin.todo.create`） |
| MCP Tool | 外部 MCP Server 提供的工具 | `McpToolBridge` | `mcp.{server}.{tool}` |

调用链示意：

```
LLM 选择工具 → DynamicToolRegistry 中的 BuiltinTool
                  │
                  ├─ 普通 Tool → ToolContract.execute() → 直接执行
                  │
                  ├─ handoff_to_* → AgentExecutor.execute()
                  │                  → 启动独立 AgentLoop（独立预算、独立上下文）
                  │                  → 子 Agent 内部再调用 Tool
                  │
                  ├─ skill.* → SkillLifecycleManager.activate()
                  │             → 启动 SubAgent（Skill 的 systemPrompt + allowedTools）
                  │             → SubAgent 内部再调用 Tool
                  │
                  └─ mcp.* → McpClient JSON-RPC → 外部进程执行
```

关键推论：**权限控制的统一收口点是 Tool 可见性**。Agent 和 Skill 的 `allowedTools` 白名单控制的不是"谁能调用我"，而是"我作为 SubAgent 运行时能看到哪些 Tool"。

### 9.2 问题分析

当前系统已有分散的权限机制（`AgentDefinition.allowedTools`、`SkillDefinition.allowedTools`、`GuardrailEngine` 风险审批），但缺少统一的权限解析模型。需要解决的核心问题：

- Workflow 步骤没有工具权限声明，直接调用工具无白名单约束
- 基础工具（§8）需要"始终可用"语义，不应被调用者白名单过滤掉
- SubAgent 的工具范围应严格为父 Agent 的子集，当前未强制约束
- 没有统一的权限解析流程把各层串起来

### 9.3 三层权限模型

权限检查由外到内逐层收窄，每一层都是前一层的子集：

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1: 全局策略（Global Policy）                          │
│  GuardrailEngine 强制执行，所有调用者都必须经过                 │
│  • ToolRiskPolicy — 风险等级审批                              │
│  • BudgetLimitPolicy — Token 预算限制                        │
│  • RateLimitPolicy — 速率限制                                │
│  • ContentSafetyPolicy — 内容安全                            │
│  • DataRedactionPolicy — 数据脱敏                            │
├─────────────────────────────────────────────────────────────┤
│  Layer 2: 调用者作用域（Caller Scope）                        │
│  每种调用者类型有自己的工具白名单机制                            │
│  • Agent: allowedTools 白名单                                │
│  • Skill: allowedTools 白名单                                │
│  • Workflow: 步骤级 required-tools 声明                      │
│  • SubAgent: parentScope ∩ selfScope（强制子集约束）          │
├─────────────────────────────────────────────────────────────┤
│  Layer 3: 工具自身属性（Tool Properties）                     │
│  工具注册时声明的固有属性                                      │
│  • RiskLevel → 决定审批模式（AUTO → USER_CONFIRM）            │
│  • tags: "infrastructure" → 绕过 Layer 2 白名单              │
│  • tags: "handoff" → 不可重试、受 canDelegate 控制            │
└─────────────────────────────────────────────────────────────┘
```

### 9.4 各调用者的权限解析

#### 9.4.1 Agent 调用工具

```
有效工具集 = (Agent.allowedTools ∪ infrastructure 工具) ∩ 全局策略通过
```

- `ToolBridgeAgentToolProvider.getToolCallbacks()` 按 `allowedToolIds` 过滤时，自动包含 `infrastructure` 标签的工具
- 空白名单（`allowedTools = []`）表示可用所有工具（当前行为不变）
- 每次工具调用仍经过 `GuardrailEngine.checkToolCall()` 做风险审批

#### 9.4.2 SubAgent 调用工具

```
有效工具集 = (parentScope ∩ SubAgent.allowedTools ∪ infrastructure 工具) ∩ 全局策略通过
```

- `AgentExecutor.buildAllowedToolIds()` 增加父 Agent 作用域约束
- SubAgent 声明的 `allowedTools` 中，只有同时存在于父 Agent 作用域内的工具才生效
- infrastructure 工具始终可用，不受父子约束
- 这确保了权限只能收窄、不能扩大

#### 9.4.3 Skill 调用工具

```
有效工具集 = (Skill.allowedTools ∪ infrastructure 工具) ∩ 全局策略通过
```

- Skill 被 `SkillToToolBridge` 桥接为 `skill.{skillId}` 工具注册到 Registry
- 当 LLM 调用 `skill.*` 工具时，`SkillLifecycleManager.activate()` 启动 SubAgent
- SubAgent 运行时的可见工具集由 `SkillDefinition.allowedTools` 决定
- `SecurityValidator` 在 Skill 加载时校验白名单不含 HIGH/CRITICAL 风险工具（已实现）
- infrastructure 工具对 Skill SubAgent 同样始终可用

#### 9.4.4 Workflow 调用工具

```
有效工具集 = (步骤声明的 required-tools ∪ infrastructure 工具) ∩ 全局策略通过
```

- Workflow YAML 定义中每个步骤新增 `required-tools` 字段，声明该步骤需要的工具
- WorkflowEngine 执行步骤前，校验 `required-tools` 中的工具都已注册且可用
- 未声明 `required-tools` 的步骤（向后兼容）默认可用所有工具
- 长期目标：所有 Workflow 步骤都应显式声明 `required-tools`

### 9.5 Infrastructure 工具的特殊语义

标记为 `infrastructure` 的工具具有以下特殊行为：

| 特性 | 说明 |
|------|------|
| 始终可用 | 不受任何调用者的 `allowedTools` 白名单限制 |
| 低风险 | 全部为 LOW 风险等级，不触发用户确认 |
| 不可禁用 | 不能通过白名单机制排除（Agent 的基本感官不应被剥夺） |
| 审计豁免 | 不写入 `guardrail_logs`（减少噪音，`datetime` 每次对话都会调用） |

判定逻辑在 `ToolBridgeAgentToolProvider.getToolCallbacks()` 中实现：

```java
// 伪代码
tools.stream()
    .filter(t -> allowedToolIds.contains(t.id()) 
                 || t.tags().contains("infrastructure"))
    .toList();
```

### 9.7 与现有代码的改动点

| 改动位置 | 改动内容 | 影响范围 |
|---------|---------|---------|
| `ToolBridgeAgentToolProvider` | 过滤逻辑增加 `infrastructure` 标签豁免 | Agent 工具可见性 |
| `AgentExecutor.buildAllowedToolIds()` | 增加父 Agent 作用域交集约束 | SubAgent 工具范围 |
| `WorkflowEngine` | 步骤执行前校验 `required-tools` | Workflow 工具权限 |
| `ToolContract` | `tags()` 已支持，无需改动 | 无 |
| `GuardrailEngine` | infrastructure 工具跳过审计日志 | 审计日志量 |

### 9.8 设计决策

**Q: 为什么不引入独立的 PermissionService？**
A: 当前的三层模型已经覆盖所有场景，且各层的执行点已经存在（`ToolBridgeAgentToolProvider` 做 Layer 2，`GuardrailEngine` 做 Layer 1）。引入独立服务会增加调用链复杂度，且需要重构现有管线。保持现有架构，在各执行点增加少量逻辑即可。

**Q: 为什么 infrastructure 工具不可禁用？**
A: `datetime`、`think`、`confirm` 等工具是 Agent 正常运作的基本前提。一个不知道当前时间的 Agent 无法处理日程相关请求，一个不能请求用户确认的 Agent 无法安全执行高风险操作。这些工具的风险等级为 LOW，不存在安全隐患。

**Q: Workflow 的 required-tools 是否强制？**
A: 短期内不强制（向后兼容），未声明的步骤默认可用所有工具。长期目标是所有 Workflow 步骤都显式声明，实现最小权限原则。
