# 知微主动性框架分析 — 从本质到机制

> **文档性质**：主动性框架顶层分析
> **最后更新**：2026-03-17（补充 §7-§9：OpenClaw 持续追踪机制、自驱动执行分析、设计启示）

---

## 1. 主动性的本质：为什么需要主动？

### 1.1 被动 Agent 的根本局限

当前知微是一个**纯被动 Agent**——用户说话它才响应，对话结束它就沉默。这意味着：

- 用户说"帮我关注机票价格"，Agent 回复"好的"，然后就忘了
- 用户说"下周开会前提醒我准备 PPT"，除非用户手动创建了日程提醒，否则 Agent 不会主动跟进
- 用户的长期需求（减肥计划、学习目标、项目跟踪）在对话结束后就消失了

**核心问题**：对话是短暂的，但用户的需求是持续的。被动 Agent 只能服务于对话内的需求，无法服务于跨对话的持续需求。

### 1.2 主动性要解决的核心问题

主动性的本质是让 Agent 具备**跨对话的持续服务能力**：

1. **记住**：从对话中识别出"这不是当场能解决的，需要持续关注"的需求
2. **追踪**：将这些需求转化为可追踪的目标，持久化存储
3. **检查**：定期（或事件触发时）检查目标的条件是否满足
4. **行动**：条件满足时主动通知用户，而不是等用户来问

这四步构成了主动性的完整闭环。

### 1.3 主动性 ≠ 主动通知

一个关键区分：**主动性不等于频繁推送通知**。

当前知微的 ProactiveReasoner 已经能推送通知（待办到期、日程提醒、每日总结），但这不是真正的主动性——这只是**定时检查 + 规则匹配 + 通知推送**，本质上是一个 cron job。

真正的主动性需要满足三个条件：
- **意图驱动**：通知的来源是用户表达过的需求，而不仅仅是数据状态变化
- **条件触发**：在正确的时机介入，而不是固定间隔轮询
- **自适应**：根据用户反馈调整行为，而不是一成不变

## 2. 知微当前的主动能力地图

### 2.1 已有的主动能力（信号驱动层）

```
信号源                    候选提供者              通知
─────────────────────────────────────────────────────
TodoSignalSource    →  TodoCandidateProvider    → 待办到期提醒
ScheduleSignalSource →  ScheduleCandidateProvider → 日程即将开始提醒
(时间信号)           →  DailySummaryCandidateProvider → 每日总结
(时间信号)           →  WeeklyReviewCandidateProvider → 每周回顾
```

这些是**数据驱动的确定性通知**——待办有截止日期就提醒，日程快到了就提醒。不需要理解用户意图，不需要 LLM 判断，纯规则就能搞定。

### 2.2 缺失的主动能力（意图驱动层）

```
对话历史  →  ???  →  用户长期目标  →  ???  →  条件满足时通知
```

中间的两个 `???` 就是当前缺失的核心能力：
- **意图提取**：从对话中识别出需要持续关注的需求
- **目标评估**：定期检查目标条件是否满足

### 2.3 两层主动性的关系

```
┌─────────────────────────────────────────────────┐
│  Layer 2: 意图驱动主动性（本次升级目标）           │
│  ┌─────────────┐  ┌──────────┐  ┌────────────┐  │
│  │ 意图提取     │→│ 目标注册表 │→│ 心跳式评估  │  │
│  │ (按需LLM)   │  │ (持久化)  │  │ (规则优先) │  │
│  └─────────────┘  └──────────┘  └────────────┘  │
├─────────────────────────────────────────────────┤
│  Layer 1: 数据驱动主动性（已有，保持不变）         │
│  ┌─────────────┐  ┌──────────┐  ┌────────────┐  │
│  │ SignalSource │→│ Candidate │→│ PolicyEngine│  │
│  │ (待办/日程)  │  │ Provider  │  │ (规则过滤) │  │
│  └─────────────┘  └──────────┘  └────────────┘  │
└─────────────────────────────────────────────────┘
                         ↓
                  NotificationService
```

**关键设计决策**：Layer 2 不替代 Layer 1，而是在 Layer 1 之上新增一层。Layer 1 的信号驱动通知继续工作，Layer 2 新增意图驱动的目标追踪能力。两层的输出最终都汇入 PolicyEngine → NotificationService 的统一通道。

## 3. 主动性的三个核心机制

### 3.1 机制一：意图捕获 — 从对话到目标

**问题**：用户在对话中表达的需求，哪些需要持续关注？

**分析**：不是所有对话都包含需要持续关注的需求。大部分对话是即时的（"今天天气怎么样"、"帮我写一段代码"），只有少部分包含跨对话的持续需求。

**场景分类**：

| 场景 | 示例 | 是否需要持续关注 | 现有能力 |
|------|------|----------------|---------|
| 即时问答 | "今天天气怎么样" | ❌ | ✅ 已有 |
| 即时任务 | "帮我写一段代码" | ❌ | ✅ 已有 |
| 显式提醒 | "提醒我明天开会" | ✅ 但有明确时间 | ⚠️ 需手动创建日程 |
| 条件监控 | "帮我关注机票价格" | ✅ 需要持续检查 | ❌ 缺失 |
| 长期目标 | "我想减肥到 70kg" | ✅ 需要长期追踪 | ❌ 缺失 |
| 模糊意图 | "最近想学学 Rust" | ⚠️ 可能需要跟进 | ❌ 缺失 |

**设计原则**：
- **不是每次对话都需要提取意图**——大部分对话是即时的，强制提取只会浪费 token
- **先用规则筛选，再用 LLM 提取**——OpenClaw 的哲学：确定性规则优先
- **宁可漏掉，不要误报**——错误地创建目标比漏掉一个目标更烦人

**机制设计**：
```
对话结束
  ↓
IntentTriggerDetector（确定性规则）
  检测对话中是否包含"未来时间词"、"条件请求"、"监控请求"等特征
  ↓
  无特征 → 静默结束（零 LLM 调用）
  有特征 → 触发 IntentExtractor
  ↓
IntentExtractor（LLM 结构化输出）
  从对话历史提取：意图描述 + 约束条件 + 触发类型(TIME/EVENT) + 触发条件
  ↓
GoalRegistry
  创建 UserGoal 记录，状态 PENDING
```

### 3.2 机制二：心跳评估 — 从目标到行动

**问题**：目标创建后，什么时候该通知用户？

**分析**：目标有两种触发模式：
- **TIME 类型**：有明确的时间点（"下周五之前"、"明天上午"），到时间就触发
- **EVENT 类型**：需要外部条件满足（"机票降价了"、"有新的 Rust 教程"），需要持续检查

**OpenClaw 的启示**：心跳式评估的核心不是"每次都通知"，而是"每次都检查，大部分时候静默"。

**设计原则**：
- **TIME 类型零 LLM**——时间比较是纯确定性操作，不需要 LLM
- **EVENT 类型分级处理**——先看有没有匹配的信号（确定性），没有才考虑 LLM 评估
- **LLM 评估有最小间隔**——不是每个心跳都调 LLM，而是间隔足够长才调一次
- **静默是常态**——大部分心跳周期的结果是 HEARTBEAT_OK，什么都不做

**机制设计**：
```
心跳周期触发（每 30 分钟）
  ↓
HeartbeatEvaluator 遍历所有活跃目标
  ↓
  对每个目标：
  ├─ TIME 类型 → 比较当前时间与目标时间 → 到期则标记 IN_PROGRESS（零 LLM）
  ├─ EVENT 类型 + 有匹配信号 → 标记 IN_PROGRESS（零 LLM）
  ├─ EVENT 类型 + 无匹配信号 + 距上次 LLM 评估 < 4h → 跳过
  └─ EVENT 类型 + 无匹配信号 + 距上次 LLM 评估 ≥ 4h → 调 LLM 评估
  ↓
  所有目标均无需行动 → HEARTBEAT_OK（静默返回）
  有目标需要行动 → 进入 GoalCandidateProvider → PolicyEngine → 通知
```

### 3.3 机制三：用户画像 — 从反馈到自适应

**问题**：通知在什么时候发、发什么类型的，用户最可能响应？

**分析**：当前的频率控制是"连续忽略 3 次就降频"，这是一个粗粒度的负反馈机制。缺少的是：
- **时间维度**：用户在什么时段最活跃？非活跃时段的通知大概率被忽略
- **类型维度**：用户对哪类通知最感兴趣？不感兴趣的类型应该降低优先级
- **正反馈**：用户确认了通知，说明这类通知有价值，应该维持或提升

**设计原则**：
- **纯统计，不调 LLM**——画像更新是简单的计数和比例计算
- **渐进式学习**——不是一次性分析，而是每个心跳周期顺带更新
- **影响优先级，不影响内容**——画像用于调整推送时机和类型权重，不改变通知内容本身

**机制设计**：
```
每个心跳周期（顺带执行，不额外调度）
  ↓
UserProfileAccumulator
  ├─ 从 EpisodicMemory 统计活跃时段分布（按小时计数）
  ├─ 从 GoalRegistry 统计偏好主题（目标 intention 关键词频率）
  ├─ 从 FrequencyStateManager 统计响应模式（各类型确认率）
  └─ 计算通知偏好权重（确认率高 → 权重高）
  ↓
PolicyEngine 读取 UserProfile
  ├─ 非活跃时段 → 降低非紧急通知优先级
  └─ 低确认率类型 → 自动降级为 LOW 紧急度
```

## 4. 三个机制的协作关系

```
                    ┌──────────────────────────────────────────┐
                    │              对话层                       │
                    │  用户对话 → EpisodicMemory 写入           │
                    └──────────────┬───────────────────────────┘
                                   │ 对话结束时
                                   ▼
                    ┌──────────────────────────────────────────┐
                    │         机制一：意图捕获                   │
                    │  IntentTriggerDetector（规则检测）         │
                    │       ↓ 有特征时                          │
                    │  IntentExtractor（LLM 提取）              │
                    │       ↓                                   │
                    │  GoalRegistry.create()                    │
                    └──────────────┬───────────────────────────┘
                                   │ 目标持久化
                                   ▼
┌──────────────────────────────────────────────────────────────┐
│                    心跳周期（每 30 分钟）                       │
│  ┌────────────────────────────────────────────────────────┐  │
│  │         机制二：心跳评估                                 │  │
│  │  HeartbeatEvaluator                                    │  │
│  │    遍历活跃目标 → 确定性规则 → (必要时)LLM 评估          │  │
│  │    → 目标状态更新 → GoalCandidateProvider 生成候选      │  │
│  └────────────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────────────┐  │
│  │         机制三：用户画像（顺带执行）                      │  │
│  │  UserProfileAccumulator                                │  │
│  │    统计活跃时段 + 偏好主题 + 响应模式 → 更新 UserProfile │  │
│  └────────────────────────────────────────────────────────┘  │
│  ┌────────────────────────────────────────────────────────┐  │
│  │         已有 Layer 1：信号驱动                           │  │
│  │  SignalCollector → CandidateProviders → 候选列表        │  │
│  └────────────────────────────────────────────────────────┘  │
│                            ↓ 合并候选                        │
│  PolicyEngine（读取 UserProfile 调整优先级）                  │
│                            ↓                                 │
│  ProactiveReasoner Stage 2（LLM 内容生成 + 发送决策）         │
│                            ↓                                 │
│  NotificationService                                         │
└──────────────────────────────────────────────────────────────┘
```

### 4.1 LLM 调用预算分析

**每个心跳周期的 LLM 调用情况**：

| 组件 | 调用条件 | 预期频率 |
|------|---------|---------|
| HeartbeatEvaluator | EVENT 类型目标 + 无匹配信号 + 距上次评估 ≥ 4h | 极低（大部分周期零调用） |
| ProactiveReasoner Stage 2 | 有候选需要 LLM 润色 | 低（只有产生候选时才调用） |
| IntentExtractor | 对话包含未满足请求特征 | 低（大部分对话不触发） |
| UserProfileAccumulator | 从不调用 LLM | 零 |

**对比当前架构**：当前每个有候选的心跳周期都会调 LLM（Stage 2 内容润色）。升级后，大部分心跳周期完全零 LLM 调用（HEARTBEAT_OK），只有真正需要行动时才调用。

### 4.2 与现有架构的关系

| 现有组件 | 变更 | 说明 |
|---------|------|------|
| ProactiveReasoner | 改造 | 新增 Stage 0（心跳评估 + 画像更新），保留 Stage 1-2 |
| PolicyEngine | 扩展 | 读取 UserProfile 调整优先级，自动发现 GoalCandidateProvider |
| SignalCollector | 不变 | Layer 1 信号收集保持不变 |
| FrequencyStateManager | 不变 | 频率控制保持不变，画像从中读取统计数据 |
| ResponseTracker | 不变 | 响应追踪保持不变 |
| CandidateProvider 接口 | 不变 | GoalCandidateProvider 实现此接口 |
| SignalSource 接口 | 不变 | 未来外部信号源实现此接口 |

## 5. 目标系统与现有 Skill 的边界

### 5.1 目标 vs 待办/日程

一个常见的疑问：用户说"提醒我明天开会"，这应该创建一个 UserGoal 还是一个日程？

**答案**：这取决于对话的上下文和 Agent 的处理方式。

| 场景 | 处理方式 | 原因 |
|------|---------|------|
| 用户说"帮我创建一个明天上午 10 点的会议" | Agent 调用日程 Skill 创建日程 → 日程 Skill 自动创建提醒 | 用户的请求在对话内就被满足了 |
| 用户说"下周的会议我需要准备 PPT" | IntentExtractor 提取为 UserGoal（TIME 类型，触发条件：会议前一天） | 用户的请求不是"创建日程"，而是"在某个时间点提醒我做某事" |
| 用户说"帮我关注 XX 股票，跌到 100 以下告诉我" | IntentExtractor 提取为 UserGoal（EVENT 类型，触发条件：股价 < 100） | 需要持续监控外部条件 |
| 用户说"我最近想学 Rust" | IntentExtractor 提取为 UserGoal（EVENT 类型，触发条件：发现好的学习资源时） | 模糊意图，需要 Agent 主动发现机会 |

**核心区分**：
- **待办/日程**：用户明确要求创建的结构化数据，由 Skill 工具直接处理
- **UserGoal**：用户在对话中表达的、需要 Agent 持续关注的需求，由意图提取自动捕获

两者不冲突——一个对话可能同时触发 Skill 工具调用（创建日程）和意图提取（创建 UserGoal）。

### 5.2 GoalCandidateProvider vs 现有 CandidateProvider

GoalCandidateProvider 和现有的 TodoCandidateProvider / ScheduleCandidateProvider 是并列关系，都实现 CandidateProvider 接口，都通过 PolicyEngine 统一评估。

区别在于候选的来源：
- TodoCandidateProvider：来源是待办数据的截止日期（数据驱动）
- ScheduleCandidateProvider：来源是日程数据的开始时间（数据驱动）
- GoalCandidateProvider：来源是用户目标的触发条件（意图驱动）

## 6. 总结：本次升级的核心价值

### 6.1 从"定时通知系统"到"意图驱动的主动 Agent"

| 维度 | 升级前 | 升级后 |
|------|-------|-------|
| 通知来源 | 仅数据状态变化（待办到期、日程临近） | 数据状态 + 用户长期意图 |
| 触发方式 | 固定间隔轮询 | 心跳评估（规则优先，大部分静默） |
| LLM 消耗 | 每个有候选的周期都调 LLM | 大部分周期零 LLM 调用 |
| 用户理解 | 不理解用户意图 | 从对话中提取并追踪长期需求 |
| 自适应 | 仅"连续忽略降频" | 活跃时段 + 类型偏好 + 响应模式 |

### 6.2 设计哲学

1. **确定性规则优先，LLM 仅在必要时介入**（OpenClaw 哲学）
2. **静默是常态，行动是例外**（HEARTBEAT_OK 模式）
3. **意图驱动，不是数据驱动**（从"数据变了就通知"到"用户想要的条件满足了才通知"）
4. **渐进式学习，不是一次性分析**（画像随时间自然积累，不额外消耗资源）

## 7. OpenClaw 的持续追踪机制：从心跳到炒股

### 7.1 OpenClaw 如何实现"持续追踪某件事"

OpenClaw 的持续追踪能力建立在三个核心机制上：

**机制一：HEARTBEAT.md 检查清单**

OpenClaw 的心跳不是简单的定时器，而是一个**人类可读的检查清单**（HEARTBEAT.md）。每隔 N 分钟，Gateway 向 Agent 发送心跳提示，Agent 读取 HEARTBEAT.md 中的条目，逐项检查条件是否满足：

```markdown
# HEARTBEAT.md（示例）
- 每 30 分钟检查一次 GitHub PR 是否有新评论
- 如果 AAPL 股价跌破 $180，立即通知用户
- 每天 9:00 生成昨日工作总结
- 如果用户的航班状态变更，立即通知
```

关键特性：
- **人类可读**：用自然语言描述检查条件，Agent 用 LLM 理解并执行
- **Agent 严格遵循**：心跳时 Agent 只做清单上的事，不自由发挥
- **大部分时候静默**：检查完所有条目，如果没有需要行动的，返回 `HEARTBEAT_OK`

**机制二：动态清单更新**

HEARTBEAT.md 不是静态的——Agent 可以在对话中动态修改它：

```
用户：帮我每天关注一下 GitHub 上 rust-lang/rust 的新 issue
Agent：好的，我已经把这个加到心跳检查清单了。
       （Agent 修改 HEARTBEAT.md，新增一条检查项）
```

这意味着用户的每一个"帮我关注 XXX"请求，都会转化为心跳清单中的一个条目，实现了**从对话到持续追踪的闭环**。

**机制三：Cron Jobs（精确时间任务）**

除了心跳检查，OpenClaw 还支持 Cron 表达式驱动的精确时间任务：
- 每天 9:00 生成日报
- 每周五 17:00 发送周报
- 每月 1 号检查订阅续费

Cron Jobs 与心跳的区别：Cron 是"到时间就执行"，心跳是"定期检查条件是否满足"。两者互补。

### 7.2 OpenClaw 炒股的实现原理

用 OpenClaw 炒股的用户，实际上是组合了以下能力：

1. **外部 API 接入**：通过 MCP 工具连接券商 API（获取持仓、下单）和行情数据 API（获取实时/延迟报价）
2. **心跳检查**：HEARTBEAT.md 中写入交易策略条件，如：
   - "如果 AAPL 跌破 $180 且 RSI < 30，买入 10 股"
   - "如果持仓 TSLA 盈利超过 15%，卖出一半"
3. **Agent 判断力**：Agent 不是简单的阈值触发器——它读取策略条件后，调用行情 API 获取数据，然后用 LLM 评估当前市场环境是否真的适合执行策略。这种"有判断力的执行"是 OpenClaw 区别于传统量化交易脚本的地方。
4. **执行闭环**：条件满足 → Agent 调用券商 API 下单 → 记录交易日志 → 更新持仓状态

**成本**：根据心跳频率和上下文大小，大约 $5-30/天（Claude Opus），高频交易场景更贵。

### 7.3 OpenClaw 模式的优势与局限

**优势**：
- 极其灵活——任何能用自然语言描述的检查条件都能追踪
- 动态可调——用户随时通过对话增删检查项
- 有判断力——不是死板的阈值触发，Agent 能理解上下文

**局限**：
- **每次心跳都调 LLM**——即使所有条件都不满足，Agent 也需要读取清单、理解条件、调用工具检查，这意味着每次心跳都有 LLM 成本
- **无确定性快速路径**——所有条件判断都经过 LLM，没有"时间比较"这种纯规则可以跳过 LLM 的优化
- **单用户设计**——OpenClaw 是个人 Agent，不需要考虑多用户场景下的资源竞争

### 7.4 知微可以借鉴什么

| OpenClaw 特性 | 知微的对应设计 | 差异 |
|--------------|--------------|------|
| HEARTBEAT.md 检查清单 | GoalRegistry（user_goals 表） | 知微用结构化数据库代替纯文本文件，支持状态管理和查询 |
| 动态清单更新 | IntentExtractor → GoalRegistry.create() | 知微通过意图提取自动创建目标，而非 Agent 直接编辑文件 |
| 每次心跳都调 LLM | HeartbeatEvaluator 确定性规则优先 | 知微的核心优化：TIME 类型零 LLM，EVENT 类型有最小间隔 |
| Cron Jobs | ScheduledTaskService（已有） | 知微已有定时任务能力，可直接复用 |
| 外部 API 接入 | MCP 工具生态（已有） | 知微已有 MCP 支持，未来可接入行情等外部数据源 |
| Agent 执行交易 | Phase 1 不支持，Phase 2 考虑 | 知微 Phase 1 仅通知，不自动执行 |

## 8. 自驱动执行：Phase 1 通知 vs Phase 2 行动

### 8.1 为什么需要讨论自驱动执行

OpenClaw 的炒股场景揭示了一个关键能力：Agent 不仅能"发现条件满足"，还能"自动执行动作"（下单、发邮件、创建 PR 等）。这引出一个问题：知微是否也需要这种自驱动执行能力？

### 8.2 自驱动执行的价值

自驱动执行让 Agent 从"通知者"升级为"执行者"：

| 场景 | 仅通知 | 自驱动执行 |
|------|-------|-----------|
| 机票降价 | "机票降到 ¥800 了，要买吗？" | "机票降到 ¥800，已帮你预订，确认付款？" |
| PR 有新评论 | "你的 PR 有 3 条新评论" | "你的 PR 有 3 条评论，已回复格式问题，其余需要你看" |
| 日报生成 | "该写日报了" | "日报已生成草稿，请确认后发送" |
| 股票止损 | "TSLA 跌破止损线了" | "TSLA 跌破止损线，已卖出 50 股" |

自驱动执行的价值是显而易见的——减少用户操作步骤，提升效率。

### 8.3 为什么 Phase 1 不做自驱动执行

尽管价值明确，Phase 1 选择"仅通知"有充分理由：

1. **信任建立**：用户需要先观察 Agent 的判断力是否可靠（意图提取准不准、时机对不对），才会信任它自动执行。如果 Agent 连通知都发不准，自动执行只会造成灾难。

2. **Guardrail 依赖**：自动执行需要完善的安全护栏——哪些操作可以自动执行、哪些需要确认、执行失败如何回滚。知微的 Guardrail 模块目前是空壳，不具备支撑自动执行的能力。

3. **复杂度控制**：Phase 1 的核心目标是建立"意图捕获 → 目标追踪 → 条件评估 → 通知"的完整闭环。在这个闭环稳定之前，叠加自动执行只会增加调试难度。

4. **可逆性**：通知是可逆的（用户忽略即可），但执行是不可逆的（下了单就下了）。Phase 1 应该选择风险更低的路径。

### 8.4 Phase 2 的自驱动执行蓝图

当 Phase 1 的"意图捕获 → 目标追踪 → 条件评估 → 通知"闭环稳定运行后，Phase 2 可以在此基础上叠加自驱动执行：

```
Phase 1 闭环（已稳定）
  条件满足 → 通知用户 → 用户手动操作

Phase 2 扩展
  条件满足 → 生成执行计划 → Guardrail 风险评估
    ├─ LOW 风险 → 自动执行 + 事后通知
    ├─ MEDIUM 风险 → 生成草稿 + 一键确认执行
    └─ HIGH/CRITICAL 风险 → 仅通知，不自动执行
```

Phase 2 的前置条件：
1. Guardrail 模块从空壳升级为可用状态（风险分级、执行审批、回滚机制）
2. Phase 1 运行足够长时间，积累了用户对 Agent 判断力的信任
3. 工具生态足够丰富（MCP 接入外部 API：邮件、日历、文件系统等）

## 9. 对知微设计的启示与总结

### 9.1 从 OpenClaw 学到的核心理念

1. **检查清单模式**：将用户的持续关注需求转化为结构化的检查清单（知微用 GoalRegistry），心跳时逐项检查，有事行动，没事静默。这个模式简单、可靠、可解释。

2. **动态可调**：用户随时可以通过对话增删检查项（知微通过 IntentExtractor 自动捕获 + REST API 手动管理）。系统不是一次性配置的，而是随用户需求动态演化的。

3. **外部数据接入是关键**：OpenClaw 炒股的核心不是 Agent 多聪明，而是它能通过 MCP 工具访问实时行情数据。知微未来的主动性上限，取决于能接入多少外部数据源。

### 9.2 知微与 OpenClaw 的关键差异

| 维度 | OpenClaw | 知微 |
|------|---------|------|
| 条件评估 | 每次心跳都调 LLM 理解自然语言条件 | 确定性规则优先，LLM 仅在必要时介入 |
| 检查清单 | 纯文本文件（HEARTBEAT.md） | 结构化数据库（user_goals 表 + 状态管理） |
| 执行能力 | 可自动执行（调用工具完成任务） | Phase 1 仅通知，Phase 2 再加执行 |
| 用户画像 | 无（单用户，Agent 通过对话历史理解用户） | 有（统计驱动的 UserProfile，优化推送策略） |
| 成本模型 | 高（每次心跳都有 LLM 成本） | 低（大部分心跳零 LLM 调用） |
| 部署模式 | 云端 Agent（持续运行） | 本地 JAR（按需启动，心跳由定时任务驱动） |

### 9.3 Phase 1 的设计边界总结

Phase 1 的目标是建立完整的"意图驱动主动性"闭环，具体边界：

**做什么**：
- 从对话中自动捕获需要持续关注的需求（IntentExtractor）
- 将需求转化为可追踪的目标（GoalRegistry）
- 心跳式评估目标条件（HeartbeatEvaluator，规则优先）
- 条件满足时通知用户（GoalCandidateProvider → PolicyEngine → 通知）
- 渐进式学习用户偏好（UserProfileAccumulator）
- 提供目标管理 REST API（查看、完成、放弃）

**不做什么**：
- 不自动执行动作（仅通知）
- 不接入外部数据源（EVENT 类型目标的条件评估依赖 LLM 推理，不主动拉取外部数据）
- 不支持用户自定义心跳检查清单（目标由意图提取自动创建，不支持手动编写检查条件）
- 不支持多用户（单用户 UserProfile）

### 9.4 未来演进路径

```
Phase 1（本次）：意图驱动的通知闭环
  ↓
Phase 2：自驱动执行 + Guardrail 风险控制
  ↓
Phase 3：外部数据源接入（行情、天气、新闻等 MCP 工具）
  ↓
Phase 4：用户自定义检查清单（类似 OpenClaw 的 HEARTBEAT.md，但结构化）
```

每个 Phase 都建立在前一个 Phase 的稳定运行之上，渐进式增强主动性能力。
