# 一键交付工作流

你将执行一套完整的代码交付流程。每一步失败都**立刻停止**并报告原因，不要跳过。

## 模式

- `/ship` 或 `/ship <描述>` — **完整模式**：测试→审查→自动修复→回归验证→文档同步→提交→PR
- `/ship check` 或 `/ship check <描述>` — **检查模式**：只执行 Step 1-4（确定范围→测试→审查→文档），**不提交、不建 PR**

解析参数时：如果第一个词是 `check`，进入检查模式，剩余部分作为功能描述。

## 输入

用户可能提供功能描述作为参数（如 `/ship 完成了用户偏好设置`）。如果没有提供，从 git diff 推断。

## 流程

### Step 1: 确定变更范围

```bash
git diff develop --stat
git log develop..HEAD --oneline
```

如果没有任何改动，告诉用户"没有需要交付的变更"并停止。

### Step 2: 运行测试

根据变更范围决定运行哪些测试：

- 有 `.java` 文件变更 → `mvn test -q`
- 有 `.vue/.ts/.tsx` 文件变更 → `cd zhiwei-web && npm run test:run`
- 两者都有 → 并行运行

**测试失败 → 停止，报告失败的测试和错误信息。**

### Step 3: 代码审查

启动 `code-review` agent 审查当前分支所有改动。

如果有 **🔴 阻塞问题**：
- 列出所有阻塞问题
- 询问用户是否要先修复（推荐）还是继续

### Step 4: 自动修复

根据 Step 3 的审查结果，自动修复**可以安全修复**的问题：

**直接修复（无需确认）：**
- 🔴 阻塞问题 — 全部修复
- 🟡 建议中的机械性改进 — 重复代码提取、命名规范、缺失注释等

**跳过（需人工判断）：**
- 涉及架构决策的建议
- 可能改变行为语义的重构
- 既有技术债（不属于本次变更引入）

如果有任何修复，进入 **Step 4.1 回归验证**：重新运行 Step 2 的测试，确保修复没有引入新问题。测试失败 → 回滚修复，报告原因。

如果审查无问题或只有跳过类建议，直接进入 Step 5。

### Step 5: 文档同步

检查改动是否涉及：
- 公共 API 变更
- 配置项变更
- 新模块/新功能

如果涉及，启动 `docs-code-sync` agent 更新文档。
如果不涉及，跳过此步。

### Step 6: 提交代码（检查模式跳过）

> **检查模式在此停止**，输出检查报告后结束。

1. `git add` 相关文件（不要 `git add -A`，排除敏感文件）
2. 基于变更内容生成规范的 commit message，格式：`<type>(<scope>): 中文描述`
3. 执行提交

### Step 7: 创建 PR（检查模式跳过）

1. 确保当前分支已推送到 remote
2. 使用 `gh pr create` 创建 PR 到 `develop`
3. PR 描述包含：变更摘要、测试结果、审查结论

### Step 8: PR Review（检查模式跳过）

1. 使用 `gh pr diff` 获取 PR 的完整 diff
2. 启动 `code-review` agent 对 PR diff 进行最终审查
3. 将审查结果作为 PR comment 发布（`gh pr comment`）
4. 如果有 🔴 阻塞问题，明确告知用户需要修复

## 输出

### 完整模式
```
## 交付报告
- 测试：✅ 全部通过（后端 X 个 / 前端 Y 个）
- 审查：✅ 无阻塞问题 / ⚠️ N 个建议
- 修复：✅ 已修复 N 项 / ⏭️ 无需修复
- 文档：✅ 已同步 / ⏭️ 无需更新
- 提交：<commit hash> <type>(<scope>): 描述
- PR：<PR URL>
- Review：✅ 已发布审查评论
```

### 检查模式
```
## 检查报告
- 变更范围：X 个文件
- 测试：✅ 全部通过（后端 X 个 / 前端 Y 个）
- 审查：✅ 无阻塞问题 / ⚠️ N 个建议
- 文档：✅ 已同步 / ⏭️ 无需更新
→ 检查通过，可以运行 /ship 完成交付
```
